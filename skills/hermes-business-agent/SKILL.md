# hermes-business-agent · 把 Agent 接进真实业务流程（或从零开发 Agent 驱动的业务系统）

## 这条主线怎么读

一条工作流：**〔入场检查〕→ 定业务 → 定形态 → 跑通内核 → 接进界面 → 赋业务能力 → 立闸门 → 取证 → 交付 →〔回路〕**。

各步性质不同，读法也不同：**入场检查**是一次性核查（工具链与语义基线可信不可信），**第 ①② 步是决策**（在纸面上确定，产出物是表与文字），
**第 ③④⑤⑥ 步是编码**，**第 ⑦⑧ 步是验证与收尾**，**回路**是上线后按节奏重复的循环。中间八步按时序读；入场检查与回路**不是步骤**——
它们是"任一出口条件不过或上游漂移时你回到的地方"。

工作量真实分布：**第 ① 步（业务契约）与第 ⑤ 步（把业务能力做成工具面）吃掉大头**，第 ⑥ 步（闸门）次之；
第 ③④ 步有现成骨架可抄，第 ⑦⑧ 步复用脚本。项目失败的原因几乎从来不是代码写错，而是第 ① 步没盘清、第 ② 步没在开工前确定——
所以这两步排在最前，且要求在开工前一次确定。

任一步的出口条件不过，**不是往下走，是进 Debug 闭环**（复现 → 定位 → 修复 → 干净环境复测 → 沉淀，见
[`references/17-debug-discipline.md`](references/17-debug-discipline.md)），修完回到本步重验；结论唯一沉淀位是
[`docs/troubleshooting.md`](docs/troubleshooting.md)。Debug 不占工作流步骤，任何一步都适用。

**每一步内部也是一条流程，不是一堆清单。** 八步之外还有第二层时序：每一步的正文都按**四拍**走——
**输入（上一步交给你什么）→ 动作（按什么顺序做，顺序错了要返工什么）→ 产出（本步交给下一步的东西）→
出口判据（拿什么证据说"本步做完了"）**。判据和动作在这一步里出现的顺序，就是它们真实发生的顺序。
只有"任一命中就触发"的判据集（如第 ⑥ 步的故障类型、第 ⑦ 步的断言集）才允许并列，且每条要写明它把流程带回哪一步。
把本步的动作铺成"参考资料 A/B/C/D 各说一件事"的清单，等于把顺序信息丢掉——那是本技能最常见的组织缺陷，
`19` 全文按这条规则重排过，可作为写法样板。

**行文标准**：正文要让**不懂技术的业务负责人、财务、一线操作员也读得懂**——先说这一步在业务上是件什么事，再说它在代码上是什么；
术语（toolset、快照、面、幂等）首次出现时跟一句白话解释；禁止用缩写、内部代号、英文从句代替说明。
精确的参数名、行号、实测数值不放正文，一律收在 `references/` 对应文档里，正文只留指针。

一句话概括内核：`pip install hermes-agent` → `from run_agent import AIAgent` → 在你的进程（或你的服务的进程）里构造 Agent、
用回调把它的输出接出来、把你的业务能力注册成工具、用 `HERMES_HOME` 圈住它的运行数据，然后按门禁验证并打包。
**Hermes 是会随使用积累记忆与技能的"数字同事"**（官方术语 self-improvement loop，见
[`references/00-index.md`](references/00-index.md) §2），做业务智能体应按这个姿态设计，
而不是当成一次性的 API 调用——这也是"接进业务"和"调个模型接口"的全部区别。

两种入场的差别只在第 ①② 步的输入，不改变主线：接进已有系统时，业务要素是**读出来的**（读现有权限表、数据模型、状态机）；
从零开发时，业务要素是**定出来的**（你先设计权限模型与口径，Agent 才可能有正确的面）。后者反而更省事——不用迁就历史包袱，
所以从零开发默认走三系统分离（业务层一开始就不碰 Agent，见第 ② 步）；接进已有系统则按 `18` 的判据权衡改造成本。

## 〔入场检查〕工具链没漂、语义有源（非步骤；开工前与每次升级后各一次）

这一步核查的**不是你的项目，是本技能的断言还可不可信**。它独立于主线八步之外，因为触发时机是"版本变了"，不是"任务开始了"。

**版本漂移。** 本技能全部 API 断言锁定在 `hermes-agent` 的某个确定版本（`scripts/api-baseline.json` 的 `baseline_version`，当前 0.19.0），
而 Hermes 发版频繁。跑 `python scripts/track_upstream.py --quick` 与 `python scripts/check_api_signature.py`：
一旦出现 `REMOVED` 或 `DEFAULT_CHANGED`，**先更新技能文档与基线再开工**，不要带病作业——漂移的签名会让回调静默不触发，
排查成本远高于此处多花两分钟。四条跟踪线里只有 **③ 源码签名**（等价于 `check_api_signature.py` 退出码 0）是开工条件：
**① PyPI 版本线是情报**——基线固定在某一版，上游一发新版它就报 DRIFT、退出码变 1，却不表示本技能失效；
**② 文档指纹 / ④ API 参考新鲜度**是维护动作（`--update-docs` / `--regenerate-apiref` 各自消掉），也不是开工条件。
发布门禁 `release_gate.py` 里的 `track_upstream --gate` 因此把四条线全部降为提示、恒返回 0，
真正的硬阻断交给 `quality_check` 内的签名段。
本地升级过 `hermes-agent` 后，再跑 `python scripts/track_upstream.py --regenerate-apiref`
重生成 `references/api-reference/`（由 `scripts/gen_api_reference.py` ast 静态解析本机已装源码得到，按模块拆分），
它既是第 ⑤ 步查精确签名的落点，也是漂移跟踪的第四线。四条跟踪线的机制与应对见
[`references/07-quality-gates.md`](references/07-quality-gates.md) §2。

**语义有源。** 三类问题三个权威源，别混用：

- 业务概念与 Hermes 语义（toolset、skill、session、`HERMES_HOME`、危险命令审批等）→ 查 [`hermes-llms-full.txt`](hermes-llms-full.txt)，
  这是官方文档的完整导出（当前基线的体积与行数见 [`references/00-index.md`](references/00-index.md) §1，禁止在此复述数值——它会随 `--update-docs` 变），
  检索地图见 [`references/00-index.md`](references/00-index.md) §1。
  注意它对「Library 如何被调用与集成」覆盖极薄：官方只有 `guides/python-library` 一页，`## Callback Surfaces` 一节
  只提到 16 个构造器回调中的 8 个，桌面界面最常挂的 `event_callback`、`tool_start_callback`、`tool_complete_callback`、
  `notice_callback` 等另外 8 个通篇没有（哪 8 个见 [`references/00-index.md`](references/00-index.md) §1.2，
  16 个回调的参数含义见 [`references/01-library-api.md`](references/01-library-api.md) §3.6.6）。
- `AIAgent` 的签名、参数、回调 → 查 [`references/01-library-api.md`](references/01-library-api.md)（源码派生并标了行号），
  要精确到参数类型与默认值时查 `references/api-reference/`。
- **文档与源码冲突时以本地已装源码为准**，并把结论记进 [`docs/troubleshooting.md`](docs/troubleshooting.md)——这是唯一的沉淀位置。

**环境可跑性核查（同一次做完，任一不过就停在原地解决）：**

1. **装包**：正确包名是 **`pip install hermes-agent`**；禁止 `pip install hermes`（那是 Helmholtz 的科研元数据工具，同名 CLI，装错会命令冲突）。
   发行包名 ≠ 导入名：装完是 23 个顶层模块平铺进 site-packages（`run_agent`、`agent`、`tools`、`toolsets`、`gateway`、`hermes_cli`…），
   **导入写 `from run_agent import AIAgent`**，而不是 `from hermes_agent import ...`。**Python 版本硬约束 `>=3.11, <3.14`**，两侧越界都装不上。
   extras 按路线选（`[all]` 极重；FastHTML+pywebview 路线通常需 `[web]`，原生或本地桥接路线用基础包即可——最小依赖是打包能瘦身的前提），
   模块全清单、extras 逐路线与 `HERMES_HOME` 的唯一真相见 [`references/05-install-and-env.md`](references/05-install-and-env.md)。
2. `python scripts/probe_library.py` —— 确认版本、安装路径、`AIAgent` 可导入。
3. **`HERMES_HOME` 已定且可写**：它决定会话/记忆/技能/日志全部落点。库不感知打包与否——冻结交付必须由启动器显式钉根，否则退回平台默认根；禁止按 EXE 包内临时目录相对算根（R8，写法见 [`references/05-install-and-env.md`](references/05-install-and-env.md) §3）。
4. **凭证**走环境变量或 provider 默认凭证源，不要写死在代码里。
5. **宿主的主线程事件循环模型**已想清楚：worker 线程起在哪、事件回传的队列/桥接落在哪个原语（Tkinter `root.after` / Qt `Signal` /
   FastHTML 生成器→SSE / 本地桥接→前端）。

> 出口判据（要能指认证据，不靠自我确认）：`check_api_signature.py` 退出码 0（即 ③ 签名线无 `REMOVED`/`DEFAULT_CHANGED`，这是唯一硬条件）；
> `track_upstream.py` 跑过且其 ①②④ 三条的 DRIFT 已按上文归类为情报或已消掉；`probe_library.py` 报告版本与基线一致且 `AIAgent` 可导入；
> `HERMES_HOME` 路径已写出且实测可写。缺任一项就停在这里。

## 第 ① 步 定业务：把业务盘成契约（本步最要紧的一页纸）

**输入**：业务方交来的材料，加上一句还没写下来的业务诉求。**产出**：一页契约表，后面七步都从它取参数。
本步与 `19` 是同一趟流程——`19` 逐站写清了每一站的输入、动作、产出与出口判据，本节只给主线读法，禁止在此重复细节。
它是整条工作流里唯一"一次确定、后面只执行"的环节：产出物落到项目里——写进项目 README，或独立成一份契约文档（惯例名 `biz-agent-contract.md`，放哪由项目自己定）。

1. **先收料，再开口问。** 材料分四类，缺哪类就停在哪类：业务规则（制度、审批流说明、口径定义）、数据与接口
   （表结构、字段字典、接口文档、样例数据）、现有系统材料（权限表、状态机定义、旧版手册、界面截图）、
   只有业务人员答得了的口径问题（这种问法该得什么、两个数对不上信哪个）。逐类的动作与停点见
   [`references/19-business-domain-model.md`](references/19-business-domain-model.md) §2.1「先收料」那一拍。
   两条约束在本步确定：未经核对的原始材料**不进上下文**，只落暂存位（`19` §4.1）；
   材料没读全就开问，会让盘出来的六要素**自洽而与实际不符**——这种错要到第 ⑦ 步才显形，
   表现为用例全绿、上线即错，返工得退回本步。
2. **先把目标说成三句话**：Agent 要替谁做什么事、这件事要动业务的哪些数据或接口、做错了的代价有多大。
   这三句话决定第 ⑤ 步的工具面宽窄和第 ⑥ 步的闸门强度：只有「问业务问题」的只读目标，与「会改单据/会写库」的目标，
   在安全设计与验证成本上完全不同，禁止留到集成阶段再补。不清楚业务全景时先读 [`docs/glossary.md`](docs/glossary.md)。
3. **再认入场方式，因为它决定后面是"去读"还是"去定"**（`19` §2.1）。接进已有系统时，权限、范围、不变量、权威源是
   **读出来的**——读既有权限表、行级过滤中间件、状态机定义、数据模型里的权威表，再问业务人员
   （"这种问法应该得到什么""这两个数对不上时信哪个"），风险是读漏一格没人告诉你；
   从零开发时它们**还不存在，是你要先设计的**，且顺序不可换向：
   **先定角色与允许的动词集 → 再定数据范围的可执行条件 → 再定不变量与权威源 → 最后才写第一个工具**
   （理由与验收点见 [`references/19-business-domain-model.md`](references/19-business-domain-model.md) §2.1；
   倒过来的代价是范围会以参数形式固化进每个工具签名，事后收口要全部改）。
4. **按固定顺序盘六要素**（`19` §2.2 逐问给出问什么、产出什么形状）：业务对象 → 业务操作 → 权限主体 → 数据范围 →
   口径与不变量，**加上第六问「数据源权威」**。顺序不能打乱——没有对象就无从谈动词，没有动词就问不出谁有权。
   第六问最容易被跳过，而漏掉它的错法最难发现：同一事实有两个来源时，Agent 挑一个自信地算完，从输出上看不出它挑错了。
   必须定出权威与切换条件，并显式写下已知缺口与误差（该问的填法与例见 `19` §2.2 第六问）。调研允许留"未知"格，
   但**未知必须登记成第 ⑤ 步的待办**——把未知留到写代码时用 if 补掉，是工具面失控的起点。
5. **做一次分流，这是第一个收尾动作**：六问里只有「口径与不变量」「数据源权威」适合以文本进上下文；
   「权限主体 / 数据范围 / 禁止组合」**必须以代码形式存在于工具实现里**——**把权限写进提示词等于没有权限**，
   一句判据：**提示词决定模型会不会尝试，代码决定它能不能成功**（四条可判别的失效路径、以及"提示词该用来降低摩擦"的正当用途，
   见 [`references/19-business-domain-model.md`](references/19-business-domain-model.md) §2.2 末）。
   分错一侧的后果要到第 ⑥ 步才显形，所以必须在这里分。
6. **再配验收，这是第二个收尾动作，也是本步唯一一处自己说了不算的地方**：把第 2 条那三句话逐条配上两格——
   **怎么算做对了**（业务方一眼能判断的一句话，不是"输出正确"）与**这次不做什么**，并当场取得业务方认账，
   把确认人与确认日期一起登记成一行（表形状与三条填法见 `19` §7 第 7 张；为什么这一拍不能并进口径那一问，见 `19` §2.2 收尾动作二）。
   找不到能答的人（业务方不在、答不了、要过几天才回）就把这一行登记成待办并停在本站，**禁止自行填上这两格再自行确认**——
   第 ⑦ 步的每条用例都会继承这份未经业务确认的理解。**没有这一拍，本步未过，不进第 ② 步。**
7. **最后汇编六张表**（`19` §7 按汇编顺序逐张说明供哪步用；该节共七张，**第 6 张入口表要到第 ② 步才填得出**——它需要运行时与配置行那一格）：
   面表、快照表、知识层清单、不变量表、字段契约表、本期目标与验收表——六张的列形状、逐张的填法与常见填错的样子全在 `19` §7，此处不复述。
   本步只有两格必须在主线认下来：面表的**归属列（判断题 / 计算题）在这里就填好**——它是第 ⑤ 步的裁剪依据、第 ⑦ 步的选轨依据；
   **字段级 schema 的归属模块**（如 `schemas.py`）在本步就定，禁止散在路由或提示词里（`20` §1）。

> 出口判据：**四类材料各有可指认的来源**（一份文件、一个链接、或"某人某日的答复"三选一，写不出来的那类就是没收到的那类，
> 要登记成待办而不是跳过）；六张表**每行都能回指到一句业务事实或一段既有代码**（回指不到 = 你替业务臆造了一格）；六要素的"未知"格已全部转成待办清单；
> **验收表每一行都有确认人与确认日期**（这一条与其余各步不同，它无法由开发自查——答案在业务方心里，既不在你手上，也不在已收到的材料里）；
> 面表已把每个候选工具标进三层（禁止层的意思是"根本不注册"，见第 ⑤ 步）；范围那一问的产出是**可执行的条件表达式**而不是一段中文说明。
> 从零开发项目回指不到既有代码，就回指到本轮**定出来的**那张角色表与范围条件（`19` §2.1「从零开发的强制顺序」第 1–2 条的产出）——
> "还没写代码"与"还没定权限"是两回事，后者不带进第 ② 步。

## 第 ② 步 定形态：宿主、路线、工程形态一次联合决策

第 ① 步的契约是输入。四件互相牵制的事按**依赖方向**定，不是并列勾选：
**部署入口（谁从哪儿进来）→ 决定宿主与交付形态；要不要独立的进程与鉴权边界 → 决定调用路线；
能力入口的差异能不能只落成配置行 → 决定工程形态；工程形态是前三者的结果。**

**先问一句：要不要自建界面。** 官方已有一个成品通用桌面端 Hermes Desktop（Electron，说明与设计文档随 wheel 装在
`site-packages/apps/desktop/`，`hermes desktop`（别名 `gui`）即可构建并启动），官方描述它「与 CLI 和网关跑同一个 Agent、同一套 skills 与同一份记忆」，
自带流式聊天、并排预览、文件浏览器、语音与设置界面。需求若只是"通用聊天窗口 + 官方工具面"，用它，本技能八步不适用；
要的是**你自己的业务工具面与界面**才往下走——官方桌面端不提供界面定制层。

**再定部署入口：谁从哪儿进来。** 单个业务人员装在办公机上，还是多客户端 / 远程 / 常驻服务？这直接决定宿主类别与交付形态：
渲染层/宿主的接入范式已在 [`references/04-rendering-frameworks.md`](references/04-rendering-frameworks.md) 里按 **A 类 Python 原生**
（FastHTML / Tkinter / pywebview / textual / PyQt / wxPython）、**B 类 JS 前端 + Python 后端**（Electron / React·Vue / Koa）、
**C 类其他语言宿主**（.NET / Java / C·C++ / Rust）三类逐框架写清，含各桥接落点与"不去连网关 8642"这类逐类约束；
框架不在清单内时套该文档 §15 的 B/C 类通用桥接范式，需要框架自身完整 API 时联网查官方文档。

**再定调用路线。** 调 Python Library 有 **5 条平等可选**的路线：**进程内直跑 / Hermes 网关 / spawn CLI / API Server / `/v1`**，
无先后顺序、无默认推荐（逐条的「何时选 / 进程拓扑 / 交付形态 / 新增代价 / 落地文档」见
[`references/02-integration-core.md`](references/02-integration-core.md) §2.1–§2.5；API Server 与 `/v1` 的完整手册见
[`references/15-api-server.md`](references/15-api-server.md)）。一句话判据：要独立进程边界、远程访问、平台消息入口、常驻服务、
独立鉴权 → 跨进程路线；要单进程单文件、无端口无 CORS、回调零序列化开销 → 进程内直跑。选跨进程路线时当场认下服务侧那层增量
（进程守护与崩溃自恢复、日志落点与轮转、滚动升级与可执行的回滚、多客户端并发与会话隔离，做法归
[`references/06-packaging.md`](references/06-packaging.md) §9）——它在第 ⑧ 步之前不显形，禁止到交付时才发现"服务没人守护、升级没法回退"。
本文与示例为叙述方便常以进程内直跑举例，**这只代表举例基线，不代表推荐**。

**再定能力入口：几个入口、几套配置——本段是下一段"工程形态"的判据。** 先分清两个"入口"，它们问的不是同一件事：
上面第二句问的是**部署入口**（办公机单机 / 多客户端 / 常驻服务，决定宿主与路线），本段问的是**能力入口**
（同一套系统里业务员问数、财务审核、管理层看汇总，各自被允许做什么）。两类都要在开工前认全，混着谈会得到一套没人管的权限。

一个系统里通常不只一种用法，入口不同、能做的事不同。正确的做法是**合并为一套统一的运行时**：不同任务从不同入口进来，共用同一套基础设施
（同一个内核、同一份会话与技能落点、同一套门禁），入口之间的差异**只通过运行时配置表达**——第 ① 步面表那张「场景 → 允许角色 → 审批要求」
配置表是唯一的差异源，第 ⑥ 步的闸门、第 ⑦ 步的断言和 `19` §6 的逐入口 diff 都对着它跑。禁止一见多场景就一个场景建一个 Agent
（配置各写一份、各自漂移，事后收口等于重写），也不许把差异散进路由代码（那就回到了第 ① 步"装配散落"的症状）；
合并运行时的三条代价（故障半径 / 配置表成为耦合点 / 合并运行时不等于合并数据域）与各自的应对见 `19` §7 第 6 张表末段。
**产出**是入口表（`19` §7 第 6 张：入口 → 场景 → 能力配置行 → 数据域），装配那一格的落地函数是确定性解析 API（`11` §8；禁止 §9 的采样档）。
**判据**：入口差异**全部能落成配置行** ⇒ 单工程内嵌够用；一旦出现"某个入口要独立的进程边界 / 独立数据域 / 独立发布节奏，
配置行表达不了"⇒ 那是下一段（三系统分离）或跨进程路线的信号，禁止用"再加一个 if 分支"代替这一判定。

**再定工程形态。** 上一段就是本段的输入之一；两种二选一（依赖铁律与落地步骤见
[`references/18-tristructure-architecture.md`](references/18-tristructure-architecture.md)）：

- **单工程内嵌**（默认）：中小型单一应用，直接在底座上加业务模块，一个交付物搞定。
- **三系统分离**：业务本身已是完整系统（多模块、需独立打包分发、底座需可整体替换、业务与 Agent 必须解耦、多团队不同节奏演进）。
  工程拆成 `业务系统/`（纯业务逻辑与 UI）、`连接系统/`（纯桥接、唯一装配点）、`Agent系统/`（纯净底座、零业务痕迹、可整体替换），
  依赖方向严格单向、**业务系统禁止 `import` 任何 Agent 模块**；三目录的职责边界、装配函数做什么、落地五步见 `18` §2.1 与 §3–§5。

**这四件必须自洽，非法组合不许凑。** 判据里**工程形态以"进程边界"为分界**：进程内直跑配三系统分离合法（`连接系统/` 就是那个进程内的
唯一装配点），跨进程路线配三系统骨架则不成立——此时已不存在"在同一进程内把业务装配进 Agent"这件事。
路线 × 形态的逐格合法性、不合法时的两种处置与定不拢时的优先序，见 `18` §4.1。唯一不能被这一句回避的是能力入口那一问：
它必须落成配置行（`19` §7 第 6 张），否则就是多处入口。

**最后在本步确定工程的组织约束。** 六条都在开工前确定，写下它们只需几分钟；第 ⑤ 步业务代码铺开之后再回头调整，代价是整层重写——所以它们属于本步：

- ①–⑤ 的细则（目录与依赖方向、Agent 集成代码独立成模块、工具函数的实现口径、规模与外发红线、回归半径与回退方式各写一句话）见
  [`references/18-tristructure-architecture.md`](references/18-tristructure-architecture.md) §2.3；
- ⑥「改动进仓的单元与签认人」的细则（留痕处所三选一、提交信息的编号形状、一次评审最少要看到什么才算可审）见
  [`references/20-output-contract-and-golden-set.md`](references/20-output-contract-and-golden-set.md) §5.1。
- 本步只有一格不许挪走：**回归半径与回退方式那两句话必须由本项目在此刻自己写出来**。第 ⑦ 步「覆盖宿主原有功能」要跑哪些用例、
  第 ⑧ 步观察窗盯哪几条基线都由第一句圈定；细则文档给的是写法与判据，替不了这一次落笔。

> 出口判据：一段话写清「目标 → 部署入口 → 宿主 → 路线 → 能力入口与配置 → 工程形态」，且这六句**彼此不自相矛盾**（每句能回指到第 ① 步的某张表）；
> 入口表（`19` §7 第 6 张）已逐行填齐，且**答得出"下一个新能力接进来，改动落在配置表加一行还是代码加一条链路"**——
> 答"加链路"或答不出，即本步未过（那说明入口差异还散在代码里，权限有多处入口要各管一遍，见 `19` §2.2 失效路径 4）；
> 上面六条组织约束已落成文字（目录、模块归属、schema 归属、外发红线、回归半径与回退方式、改动进仓的单元与签认人）。缺一句或自相矛盾就留在本步，不带进第 ③ 步。
> **这道门由开发自行判定**：六句决策是否互相矛盾、回归半径与回退方式有没有写，都是可自查的事实。整条主线唯一一处需要向业务方**新取**背书的
> 出口在第 ① 步的验收表（`19` §7 第 7 张）；第 ⑤ 步那道"改期望值换人签"与第 ⑧ 步那份制品上的演示记录，用的都是这张表上已认过的同一行，
> 属旧背书的核对，不另设取背书环节。本步不重复请业务方确认——把纯工程决策拿去请业务方确认，只会得到一句对方答不出的
> 「按你说的办」，反而多一处没有信息量的记录。

## 第 ③ 步 跑通最小可对话内核

**输入**：第 ② 步划好的目录与形态。**产出**：一个「一句话进、一句话出、流式可见」的空壳——此时**还没有一行业务代码**。
先拿到这个空壳，再谈业务。铁律是**复制-适配-加你的业务，不改造底座**：
底座要复制进第 ② 步划好的目录里跑，禁止在 `examples/` 或 `templates/` 原目录内就地开发、就地建 venv。

**起点选一个（都可直接复制）：**

- [`examples/01-hermes-desktop/`](examples/01-hermes-desktop/) —— 旗舰参考实现，已是三系统完整形态：
  [`业务系统/`](examples/01-hermes-desktop/业务系统/README.md) 给纯业务样例，
  [`连接系统/`](examples/01-hermes-desktop/连接系统/README.md) 给装配范式，
  `Agent系统/`（git submodule，克隆后需 `git submodule update --init`）是纯净底座。单工程内嵌就取 `Agent系统/`，三系统分离就整套照搬。
- [`templates/fasthtml_minimal/`](templates/fasthtml_minimal/) 或 [`templates/tkinter_minimal/`](templates/tkinter_minimal/) —— 只要一个最小骨架时用。
- [`examples/02-hermes-pywebview-multiagent/`](examples/02-hermes-pywebview-multiagent/) —— 纯 pywebview 极简 + 多 Agent 编排；
  [`examples/03-nesquena-hermes-webui/`](examples/03-nesquena-hermes-webui/) —— 三栏 Web 界面、与 CLI 1:1 对等
  （`api/agent_runtime.py` 里 `from run_agent import AIAgent`）。

**构造 Agent 的六条硬性规定**（六条同时生效、落在同一个构造点上，不是先后顺序；参数全表见 [`references/01-library-api.md`](references/01-library-api.md) §3，回调见 §4）：

- **绝不复用 `AIAgent` 实例**，每次对话新建。它内部持有会话历史、工具会话、迭代计数器，共享实例 = 会话串台 + 计数器错乱。
- **绝不在主线程/事件循环里直接调 `run_conversation()`**。它是阻塞同步调用，主线程调 = 冻界面。必须 worker 线程 + `queue.Queue`。
- **流式不靠返回值，靠回调，且两类回调位置不同**：文本增量给方法参数 `stream_callback`，工具/推理事件给构造函数——写反了就是"静默无流式"：

  ```python
  agent = AIAgent(..., quiet_mode=True, max_iterations=20,
                  disabled_toolsets=["terminal"],
                  tool_start_callback=cb1, reasoning_callback=cb2)   # 事件类 → 构造函数
  agent.run_conversation(user_message=..., stream_callback=cb3)      # 文本增量 → 方法参数
  ```

- **`quiet_mode=True`**：否则 Hermes 的 CLI 输出会污染 stdout 和 GUI 日志窗。
- **显式设 `max_iterations`，禁止依赖默认值**：这个参数的默认值存在"文档与源码不一致"（实测值、冲突结论与处置的唯一出处见
  [`references/01-library-api.md`](references/01-library-api.md) §3.6 第 11 行 与 [`docs/troubleshooting.md`](docs/troubleshooting.md) §11），
  业务问答建议 10~30、带多步工具的写面 20~40，防跑飞烧钱。
- **`disabled_toolsets=["terminal"]` 起步**：不跨进程的路线没有内建安全边界，放开 terminal 等于把 shell 交给模型。
  也不要写成 `enabled_toolsets=["file"]` 这类减法反向写法——那会把 web/memory/code_execution 等能力全砍掉，是功能退化；
  正确姿势恒为 `enabled=None` + `disabled` 做减法（R4，工具集语义见
  [`references/03-capabilities-and-toolsets.md`](references/03-capabilities-and-toolsets.md) §1）。

**回调里只做 `queue.put(...)`。** 回调在 worker 线程执行，禁止做重活、禁止碰 GUI 控件，渲染一律交回主线程。

> 出口判据：空壳能对话、能看到逐字流式；骨架文件 `python -m py_compile` 通过、`from run_agent import AIAgent` 可导入。此时还没有一行业务代码。
> （`scripts/quality_check.py` 的六段查的是本技能自带的 examples / templates 与文档，替不了你的工程，留到第 ⑦ 步再跑。）

## 第 ④ 步 接界面：把事件流变成业务看得见的反馈

**输入**：第 ③ 步挂好的回调与 queue。**产出**：界面上看得见的五条链路——业务人员能从这里判断 Agent 正在做什么、卡在哪，被问到时还能当场回答。
桥接范式固定为 **callback → queue → SSE/after → 前端渲染**，前四条链路（文本流、工具卡片、思考过程、错误与结束）都要有落点，
按第 ② 步选定的宿主套用 [`references/04-rendering-frameworks.md`](references/04-rendering-frameworks.md) 对应章节：
FastHTML 侧用生成器消费队列产出 SSE；Tkinter/PyQt 侧 `root.after()` / `Signal` 回主线程取事件；
Electron/React/Vue/Koa 侧经 stdio/命名管道/本地 socket 把事件推到前端；.NET/Java/C/C++/Rust 侧经嵌入调用或 IPC 转发（`04` §10–§13）。
工具调用可视化与思考过程展示都是同一套事件（`tool_start_callback` / `tool_complete_callback` / `reasoning_callback`；
`event_callback` 虽是构造参数，0.19.0 内核只经它发 `session:compress` 一个事件名，拿它当界面事件源会收到近乎空的流），
只是渲染成卡片、折叠块的区别——事件词汇表见 [`references/01-library-api.md`](references/01-library-api.md) §4.1，
旗舰示例的桥接实现是 `01` §4.2。

**第五条链路是反方向的：Agent 向人提问。** 内核自带追问通道——`clarify` 工具向用户提多选或开放问题（`03` §3.4），
构造器上的 `clarify_callback` 是它的出口，签名 `(question, choices) -> str`（`01` §3.6.6 第 54 号）；
跨进程路线另有 `tools.clarify_gateway` 的阻塞队列（`12`）。**本步必须把它接成界面上能点的选择框，并把答案原样回传**：
回调留 `None` 时 `clarify` 直接返回错误，于是 Agent 在无人可问的状态下自行选定一种理解继续执行——
这正是第 ① 步验收表要防的那件事，只是它发生在运行期，而且这一次没有任何人来确认。
它与前四条的差别要说清：前四条只出不进，这一条是进出成对——回调里拿不到答案，那一轮就停在提问处。

B 类宿主新增 JS 模块时，`scripts/check_js_modules.py` 与 `scripts/check_endpoints.py` 是这条链路的护栏
（前端路由 404 只有链路校验抓得到）。
禁止进程内形态下连 `127.0.0.1:8642`、配 `API_SERVER_KEY`、配 CORS、用 Node/Electron 包 Hermes 内核，都属于串路线的错误（R2/R3）；
若第 ② 步就选了跨进程路线，则端口与鉴权由对应服务承担，按该路线的规则走。

> 出口判据：界面上能看到逐字输出、工具调用卡片、思考折叠；worker 线程崩溃被 try/except 包住且不带走界面；错误事件走同一条 queue 通道；
> 接了 `clarify` 的，还要能当场演示一次「它问、你答、对话继续」。

## 第 ⑤ 步 赋业务：按第 ① 步的面表，把业务能力做成工具面

**输入**：第 ① 步的六张契约表、第 ③④ 步跑通的空壳。**产出**：面表上每一格都落到一个真实注册的工具，
且每个工具都带着快照段、结论 schema 与 Golden 用例。这一步和第 ① 步合起来是「业务智能体」区别于「能聊天的小工具」的地方。
总原则只有一句：**优先用 Hermes 官方预留的非侵入扩展面，不要改 `hermes-agent` 包源码**——改核 = 升级即丢失、无法 pip 同步、审计回滚困难。

**动作 1 · 给每个候选能力选一条落地的路。** 按下面 1→5 依次问，问到"是"就停，禁止一上来就写插件。
五面的完整参数与机制见 [`references/02-integration-core.md`](references/02-integration-core.md)：Skill §10 / MCP §11 / Plugin §12 /
Memory backend §13 / 进程内 toolset 三层范式 §7.1。

1. **只是要让 Agent「更懂怎么做」、不新增可调用的动作？→ Skill。** `$HERMES_HOME/skills/<name>/SKILL.md` + 脚本，放下去即生效、
   每个已装 skill 自动成为 slash 命令。**限制：Skill 不注册新工具**——需要"能调用"就别停在这一问。
2. **要动的东西在另一个系统或另一种语言里？→ MCP server。** FastMCP 或任意语言写一个独立 server 接进来，零 Hermes 源码改动。
   本步只有一条决策：**接好后立刻做工具筛选，只读面选 `select`**，别默认给一堆写权限（`19` §3 三层面的 MCP 侧落点）。
3. **要注册新工具、挂生命周期钩子/中间件、替换内置 backend？→ Plugin。** `$HERMES_HOME/plugins/<name>/`（`plugin.yaml` + `register(ctx)`），
   新工具走 `ctx.register_tool`。
4. **只是想让它跨会话记住业务画像？→ Memory backend。** 换长期记忆后端走配置或注册 `MemoryProvider`。
5. **都不是，能力就是一段纯 Python 且与本机界面紧耦合？→ 进程内自定义 toolset**（第五条路，三层范式见 `02` §7.1；
   工具集是 `enabled_toolsets`/`disabled_toolsets` 的输入，语义先读 [`references/01-library-api.md`](references/01-library-api.md) §3.2）。

**选完再去查字典，禁止通读。** 57 个工具集（33 capability + 24 `hermes-*` 集成）逐条在
[`references/03-capabilities-and-toolsets.md`](references/03-capabilities-and-toolsets.md)；工具集之外的能力层
（Goals/Snapshots/MOA/Projects/Blueprints/Batch/Backup/Profiles/Routing）逐条在
[`references/08-capability-integration.md`](references/08-capability-integration.md)；要确认某个 `tools.*` / `agent.*` / `hermes_cli.*`
模块存不存在、能不能进程内用，分别查 `12` / `13` / `10`，支撑模块（`hermes_constants`/`hermes_state`/`toolsets`…）查 `11`。
这五份是**查证用的字典**，不是通读材料。

**动作 2 · 按面表逐格注册，顺序与动作 1 相反——从最狠的一层往下减。** 逐工具落地前先查面表：禁止层
**根本不注册、不出现在工具列表里**（拦得住调用，拦不住模型围绕它做计划）；
受控写层注册时就要同时接上第 ⑥ 步的审批入口——**面先于闸门，但不是"先开面无闸门跑通、再回头补闸门"**；
只读层直接注册。三层面各自怎么落、与业务权限表怎么 diff，见 [`references/19-business-domain-model.md`](references/19-business-domain-model.md) §3 与 §6。

**每注册一个工具，当场过对账门。** 一个工具的最小提交单元是四件：handler 实现、该工具的 Golden 用例（量级见 `20` §4.2）、
面表上那一行、验收表「派生的 Golden 用例编号」列里那条回指（`19` §7 第 7 张）。四件拆成两次提交，前一次交付的就是一个没有回归覆盖的
能力；拆给两个人做，最后少的那一格通常是回指——它只对别人有用，不对写用例的人自己有用。核这一拍的命令是：

```
python scripts/check_golden_coverage.py --golden <用例集文件> --contract <契约表所在的 md 文件>
```

离线、无需 Key、**不执行用例**，只核这四件互相指认得通不通（12 项判据、以及它查不到的三件事，逐条写在脚本首段）。
它与第 ⑦ 步那条回归的分工：本步这道门核"有没有、对不对得上契约"，第 ⑦ 步核"行为对不对"；这道门在第 ⑦ 步开跑前还要再跑一次，
提交时那次通过不代表最后一次加完之后仍通过，两次缺一不可。四件进同一次评审、**改过期望值的那一批换人签**、评审后逐条回写并关闭——
这三拍的细则与理由见 `20` §5.1，本步的出口只认结果：那一次评审的记录在案，且期望值那一格有签认人。

**动作 3 · 写 handler 前先过三问，把每一格判给模型或代码：模型负责判断，代码负责标准化流程与固定规则。**
三问的全文版（① 给定输入输出是否唯一确定 ② 这条规则会不会在没人审阅的情况下变 ③ 出错时要不要向人解释理由）在 `19` §3 第 5 步：
**①是 且 ②否 ⇒ 归代码，一次都不给模型；③是 ⇒ 归模型**，但结论仍要回代码过校验才落库。
**判给代码的那一格不要注册成工具**——它此刻很可能正挂在一个"只读工具"上（让模型绕一轮推理去问一个能算的东西）：
改成结果在本轮开始前算好注入，或整格省掉；这同时压面宽（每少一个工具少一份 schema）。
这条线划在哪儿，决定了第 ⑥ 步的闸门有多硬、第 ⑦ 步的断言能有多确定（测试轨按归属列选，两轨混用的错法见 `20` §4.5），
也直接省下重复推理的时间与 token。禁止把固定规则写成提示词请求模型配合（`19` §4 第五档）。

**动作 4 · 上下文分两层注入，别混成一个函数。** 稳定知识（口径定义、状态机规则、数据源权威、流程说明）**版本化、人工审阅、离线维护**，
落在 Skill 面或项目的 wiki 文档；每轮会变的（当前主体 / 数据范围 / 现状计数 / 禁止事项）才是**快照**，每轮重取。
两层共用一个函数、共用一个 token 预算，后果是稳定规则被现状数据挤掉注意力、且没人对它负责
（两层最后往往拼进同一条注入通道——通道共用没关系，预算跟着共用才是根本原因）。
快照的段式、刷新时机、五档预算记账表与"范围必须由服务端推导"的强制做法见
[`references/19-business-domain-model.md`](references/19-business-domain-model.md) §4–§5；三系统形态经 `get_business_snapshot()`
装到对话侧的 `BUSINESS_CONTEXT_HOOK`，单工程形态在自定义 toolset 的构造点注入。

**动作 5 · 要结论进得来，就用强类型结构化输出。** 业务系统要的是可入库、可断言的字段，不是一段散文回答：
`ctx.llm.complete_structured(instructions=…, input=[文本/图像块], json_schema=…)` 会解析并校验 schema、结果在 `.parsed`
（异步兄弟 `acomplete_structured`），它复用宿主已配好的模型与鉴权、插件不必自带 provider key（信任覆写见 `02` §12）；
纯 Agent 对话侧的格式透传走 `request_overrides`（`01` §3.4/§3.4bis，含 OpenAI 风格多模态消息）。
schema 的五项设计判据、以及"`json_schema` 校验之后还要过业务侧二次校验与不变量断言"的顺序（模型给出类型合法但业务非法的值是常态）
见 [`references/20-output-contract-and-golden-set.md`](references/20-output-contract-and-golden-set.md) §2–§3。

**动作 6 · 面铺开后再收敛，别急着上编排。** 需要的行为恰好是某条 CLI 能力时，直接 import `hermes_cli` 的对应模块进程内调用，
不要 spawn 子进程（选了路线① 时，R1，复用清单见 [`references/02-integration-core.md`](references/02-integration-core.md) §4）。
**"多场景"不在本步定**：第 ② 步已经把它定成入口表里的配置行（`19` §7 第 6 张），本步只是照那一行注册自定义工具集
（确定性解析 API 见 [`references/11-library-support.md`](references/11-library-support.md) §8；禁止 §9 那个概率采样档，实测随时可能把禁止面抽进球面）。
本步只留一条减法原则：**先合后拆**——默认单 Agent 加对的上下文，出现"一堆同类查询工具"先把它们收敛成一个统一入口工具
（减面、减 token、减模型的选择负担），合得起来就不建第二个 Agent。确实要编排时按需求选机制（`delegation` 工具集 / Profiles / MOA /
Kanban lanes 各自的成本与前置见 [`references/21-operations-and-degradation.md`](references/21-operations-and-degradation.md) §4），
工具多到把上下文吃掉时的"搜索工具 / 读详情 / 执行"三段式发现层见 `19` §6 第 4 条。两句硬约束留在本步：
委派卡片在未实测前不得宣称支持（R6），被搜出来的工具仍受禁止面约束（Tool Search 的适用边界见
[`references/00-index.md`](references/00-index.md) §1.1）。

**动作 7 · 收尾前承认自己在哪条路线的边界外。** 消息平台接入、cron 多投递、SSH/Docker 远程 terminal 后端、网关审批分类器、
真实账单（进程内 `get_credits_*` 只是**估算**）、多客户端共享内核——这些需要常驻服务或平台消息入口，属跨进程路线；
进程内做不了，要么自建等价物，要么在第 ② 步就换路线（边界清单见
[`references/02-integration-core.md`](references/02-integration-core.md) §8）。

> 出口判据：拿第 ① 步目标那句业务事做**一次真实往返**，看三件证据——① 工具序列里出现的都是面表上的工具（没有越层）；
> ② 结果是过了 schema 的结构化字段而非散文；③ **写面执行后回读到的实际生效值与结论一致**（改完不回读就认账，是假绿最常见的形态）。
> 并且最后一次加完工具后 `scripts/check_golden_coverage.py` 已通过（它逐条核四件同提交是否成立，见本步动作 2 末）。
> 并且**本步动过期望值的那些提交，都有第 ② 步第 6 条约定那一处的签认记录**（无记录即本步未过：对账门查不到期望值对不对，这一格只能由签认人认定）。
> 并且本步收工时那一处**没有挂着未回的意见、也没有"代码已合、状态还是待开发"的条**（动作 2 末的回写要求，收在这里才收得住）。
> 用例在这里写，不在第 ⑦ 步现补——现补的用例只会覆盖你当时想得起来的工具。

## 第 ⑥ 步 立闸门：把面表里标出的风险做成强制

**输入**：第 ⑤ 步注册好的面（尤其是受控写层）+ 第 ① 步面表上标注的审批要求。**产出**：每个风险点都有一段会拒绝的代码，
而不是一句提示词。第 ⑤ 步按面表把能力开出来了，这一步把面表标注的**风险**变成代码里的强制；量级由第 ② 步的"做错代价"决定。
下面六件事按依赖顺序做——身份不知道，审批就不知道给谁；写契约没定，降级契约就无从写起。

**1 · 先确认"谁在问"这件事在哪儿解决。** 闸门之上没有身份：整条链只认"这把 key + 这个会话 id + 这个 profile"。
0.19.0 没有角色/scope 概念——用户身份只是构造器上的标签（`user_id`/`chat_id` 等，`run_agent.py` 对它们无判断分支），
工具 handler 侧只拿到平铺的 `task_id` / `session_id` / `user_task`，没有 per-request 上下文对象（逐站实测见
[`references/15-api-server.md`](references/15-api-server.md) §4ter）。所以「谁能做什么、看哪个范围」只能在 handler 内
用 `current_scope()` 从会话反查业务登录态（`19` §5），禁止采信客户端或模型自报的"我是谁"。

**2 · 给每个受控写工具配审批闭环。** 不跨进程隔离的路线没有网关那套危险命令审批分类器的触发源，审批只能在自建工具层实现：
写操作先出「待确认」事件 → 界面/业务侧确认 → 才真正执行（范式见 `03` §2 与 `02` §7.2；表格/办公场景按 `02` §7.3 的
白名单字段、可回滚、留痕三件治理）。跨进程路线绑定非本机地址时 terminal 必须进沙箱，鉴权边界由对应服务承担。
还要给确认过程加一项度量，因为**人工确认会退化成形式**：把批准率与回滚率记进日志（字段见 `21` §2.1），默认全程人工确认，
要不要放宽、按什么阈值放宽、放宽后怎么退回，判据唯一归
[`references/19-business-domain-model.md`](references/19-business-domain-model.md) §3「分级演进的入口」（主线与参考文档不各定一套数字）；
反过来批准率接近 100% 且面又宽，先怀疑是面开宽了（回 `19` §3 把该动作挪进禁止面），禁止把高批准率当 KPI 去优化。

**3 · 写操作按"目标状态 + 幂等 + 回读"三件做，禁止按"增量命令"做。** 说"把这张单据置为已审核"而不是"状态往下推一格"；
每次写带幂等键，**重试或续跑前先读当前状态**再决定要不要重发（下面第 4 条降级契约允许"拆分续跑"，没有这条就会重复执行同一笔写）；
执行完**回读实际生效值**，不一致就报不一致，禁止把"接口返回 200"当"业务已生效"。三条的落地字段见
[`references/19-business-domain-model.md`](references/19-business-domain-model.md) §3 与
[`references/21-operations-and-degradation.md`](references/21-operations-and-degradation.md) §5。

**4 · 逐类确定故障的降级契约**（provider 不可用 / 工具执行失败 / 审批被拒 / 迭代或预算耗尽）：
界面给确定文案、写面不留部分写入、审批拒绝后 不得自动重问绕过闸门、前端状态机按"错误路径不再发 done 事件"实现。
逐条契约与实现要点见 [`references/21-operations-and-degradation.md`](references/21-operations-and-degradation.md) §5。

**5 · 圈住它能写的文件与用户的运行数据。** 内置的写黑名单只是误操作护栏（源码自己声明不是安全边界），要根目录就显式设
`HERMES_WRITE_SAFE_ROOT`，要边界只能换 terminal 后端。`HERMES_HOME` 指向的既有数据是用户的业务资产：不要碰出厂 `.hermes_data`
而不备份（必须 备份→变更→还原→md5 校验），不要 `rmtree` 发布目录，不要杀用户正在运行的 EXE（R11，见
[`references/07-quality-gates.md`](references/07-quality-gates.md) §3）。
**6 · 最后自检与诚实对外。** 进程内形态不起 HTTP 服务也要能确认"底座接对了"：用 `runtime_ready()` 断言版本、可导入、四个回调参数名
都在、`stream_callback` 在方法签名里、工具注册成功（脚本见 `07` §3）。同一件事的延伸是对业务人员的承诺：**别宣称没实测的能力**
（子代理委派卡片的 `event_callback` 透传未经实测，先实测再对外说，R6），也别把估算说成实测（成本同理，R7）。

> 出口判据（两样都是能跑的东西）：跑一次 `19` §6 的面与权限 diff，**逐入口各跑一遍、按入口分组输出**（禁止只跑界面那条路；
> 合并总数会把"cron 用默认全量面"摊平成 0），输出里**禁止面逐项缺席断言通过**（不是"它被拦住了"，是"工具列表里没有它"）；
> 每个受控写工具都有「审批被拒」与「重试前先读状态」两条测试用例（用例形状见
> [`references/20-output-contract-and-golden-set.md`](references/20-output-contract-and-golden-set.md) §4.3 的 `forbidden` / `invariants`）；
> `runtime_ready()` 全绿。

## 第 ⑦ 步 取证：Check → 一次真实对话 → Golden 回归

**输入**：第 ⑤⑥ 步的实现与用例。**产出**：一份能指认的证据存档（第 ⑧ 步验收就指它，不指口头结论）。
心智模型只有两条：**Check 管「规约对不对」（静态、快、无需 API Key），Test 管「行为对不对」（跑真实集成）**。
全绿才进第 ⑧ 步；任一条不过 → 进 `17` Debug 闭环（Prove-It 先断言复现，修完在干净环境复测），回本步重跑。没有测试就不改 bug，不接受"改了没验证"。

1. **Check（静态）**：`python scripts/quality_check.py`（py_compile + 技能结构 + 离线桥接 + 签名漂移 + 网页回归 + 文档链接六段）。
   改 `.py` 必跑，改 `.js` 加 `node --check`。
2. **Test（离线，无需 Key）**：`test_bridge.py` 的离线桥接 + `python scripts/smoke_test_web.py`
   （断言关键 DOM id 与 `/healthz` 200，抓首页渲染崩溃）。
3. **Test（一次真实对话，同帧取多类证据——带 Key 的往返只跑这一次）**：按
   [`references/09-integration-e2e.md`](references/09-integration-e2e.md) 的 walkthrough 走一遍，一轮对话里同时拿到：
   `runtime_ready()` 自检 → 最小构造 + 接事件总线 → 收事件流 → **断言 `stream_callback` 确实被调用 ≥1 次**
   （很多路径会静默降级成"一次性吐全文"，不验就发现不了，这是本技能独有、绝不可省的一条）→
   专项断言 A1–A9（给一个必须用工具才能完成的任务，断言 `action`/`action_result` 配对出现）→
   **并覆盖宿主系统原有功能用例**（用行为契约断言，不比回答文本，不要把 Agent 接成会弄坏原有功能的东西）。
   **把这轮的事件流存档**——它是第 ⑧ 步验收要指的证据。
   输出质量评估用 `09` §8 的 LLM Judge 三段式（判官也复用第 ⑤ 步的 `complete_structured`），无网环境用 `09` §9 的 mock 回放做确定性测试。
4. **Test（业务 Golden 回归）**：**用例在第 ⑤ 步随工具写，这里只跑**——开跑前把第 ⑤ 步那道对账门再跑一次：
   `python scripts/check_golden_coverage.py --golden <用例集> --contract <契约表>` 必须全绿，
   不绿就不要开始记通过率（对账未过的用例集，跑出来的通过率里掺了多少无人认领的用例，数字本身看不出来）。
   通过后按面表「归属」分轨（计算题环节不得进 Golden，
   它归单元测试与离线断言；判断题环节不得用 mock 断行为，它只进 Golden 分维度，两轨混用的错法见 `20` §4.5），
   再按第 ① 步字段契约派出的形状**分维度看通过率**：
   只读面 / 受控写面 / 越权负例 / 降级四类，另加**多源冲突**与**写后回读不一致**两类负例；每工具 ≥3 正 2 负 2 边界、权限矩阵每格 ≥1 条；
   越权那一格必须含**换一个 `session_id` 重跑同一问题**：返回值不随之改变，就说明范围不是服务端推导的（`15` §4ter 那条链断在工具之前）；
   30–50 条即可上线做回归，100+ 才谈趋势（用例形状、规模基线、各段的运行位置见
   [`references/20-output-contract-and-golden-set.md`](references/20-output-contract-and-golden-set.md) §4）。
   **每条用例的期望值都要能回指到第 ① 步验收表的某一行**（那一行上有业务方认过的「怎么算做对了」）；
   回指不到的用例是开发自己给自己出的题——要么删掉，要么回去补验收表那一行并重新取得确认。
   禁止把值断言降级成"非空/包含某词"，禁止拿判官分当放行开关，禁止失败就改用例期望去"过"（先按 `20` §6 四类归因）。
5. **Test（界面，可选）**：FastHTML/pywebview 路线用 `scripts/ui_window_verify.py` 做原生窗口断言 + 截图质检，
   `scripts/ui_automate.py` 做点击/输入/导航自动化；与 `smoke_test_web.py` 互补（后者验节点存在，前者验视觉无问题）。

含真实 Key 的 LLM 往返由用户在本步执行；技能内容（签名/版本基线/路径/脚本）**任何改动**后，入场检查的漂移核查与
`release_gate` 全套都要重跑，任一硬失败即阻断。

> 出口判据：Check 全绿 + 用例↔契约对账全绿 + 那一轮真实对话的事件流存档在案（含 `stream_callback ≥ 1` 的证据）+ E2E 断言（含宿主原有功能用例）通过 +
> Golden 四类维度无越权/降级类失败 + 禁止面缺席断言通过。

## 第 ⑧ 步 交付：门禁、打包、验收、观察窗与收口

**输入**：第 ⑦ 步全绿的证据存档。**产出**：交付物本身 + 一页填完的验收清单 + 六条基线数字（下一版靠它判退化）
+ 一份观察窗约定（放量批次、窗口时长、回滚触发判据、收口方式）+ 窗收口时那一页「本期停在哪里」（它的时点在本步出口之后，见本步末拍）。
本步动作有先后：先跑门禁（不过就没有制品），再按形态打包/部署，最后填验收、把观察窗四格写定；
那一页「本期停在哪里」到窗收口才写，不在这一串动作里。

**门禁。** 打包前必跑 `python scripts/release_gate.py --verify-launch`（`track_upstream --gate` → `quality_check` → `check_endpoints` →
`smoke_test_web` → `check_js_modules` → 版本一致性 六硬门禁，再叠 `verify_launch` 真起进程验端口/健康端点/首页，全绿放行）。
六段各自的退出码语义、以及"`track_upstream --gate` 只打印漂移提示恒返回 0、签名漂移的硬阻断在它后面的 `quality_check` 内"这条分工，
见 [`references/07-quality-gates.md`](references/07-quality-gates.md) §2。其余门禁都在进程内或静态层面检查，
**没有一个真的把应用起在端口上**——`--verify-launch` 补的就是这个盲区（它把 `06` §7 的四步判据可执行化，含跑完自动终止进程、确认端口释放）。
选了路线④⑤（API Server / `/v1`）的加 `--api-server [--api-key ...]`：对**在跑的**服务做真实 HTTP 探测，服务没起则退出码 2 记 SKIP，
不阻断进程内形态；选了三系统形态的另跑 `python scripts/verify_tristructure.py`（六硬门禁 + 软门禁 `agent_zero_diff`，
检查项语义与不可判定时降级 SKIP 的规则见 [`references/18-tristructure-architecture.md`](references/18-tristructure-architecture.md) §7）；
技能自身的结构门禁是 `scripts/check_skill_gate.py`（主线引用文件齐备 + 无未登记孤儿素材）。

**打包（PyInstaller 单文件）与服务侧交付。** 冻结配方与三类只在制品现身的坑（hidden-import 缺失、根路径钉错、资源没进包）归
[`references/06-packaging.md`](references/06-packaging.md) §1–§8；选了路线②③④ 的常驻服务做法归该节 §9（禁止用冻结 EXE 上服务器、
守护层外置、制品双版本并存 + `HERMES_HOME` 备份先行、绑非本机地址前按 `15` §5 把 terminal 收进沙箱），服务侧验收在 `06` §7 四步之外再加三条：
**重启自恢复**（手动 kill 后 `/health/detailed` 回到就绪）、**预发走过一次真实回滚**、**两客户端各带自己的会话头并发对话不串台**。
**一键启动脚本**（`启动.bat` 的编码与派发规则、全局 venv 落点与 `isolated_venv` 隔离）同样归 `06` §3 与 §5；创建完必须走完 `06` §7 四步验证
（venv/依赖 → 启动 → 端口+健康端点 → 前端/窗口）才算"能启动"——前三步已由 `release_gate.py --verify-launch` 代跑（指向交付目录时用
`--launch-root`/`--launch-python`/`--launch-port`/`--expect`），第四步"窗口真打开"仍需人工或 `ui_window_verify.py` 确认。

**验收前先把"在哪儿验、验的是什么"定下来。** 四件，缺一件验收结论就搬不到生产上：

① **验的对象是制品，不是源码**——把第 ⑦ 步 Golden 里本期验收表覆盖到的那几条，在制品上重跑一遍。
② **重跑在与生产隔开的环境里**（数据用副本、`HERMES_HOME` 指向验收专用目录、模型 key 用验收专用那一个）——验收必须真写一次，
   否则第 ⑥ 步出口那两条与第 ⑦ 步那类「写后回读不一致」负例都验不到；选了路线②③④ 的由 `06` §9.8 预发承担，禁止为验收另建第四套环境。
③ **验收环境与生产的差异逐格登记**（模型与 key 来源、副本生成时间与数据范围、权限表来源、terminal 后端与 `HERMES_WRITE_SAFE_ROOT` 取值）。
④ **记下验的是哪一份制品**（单文件记可执行文件的 SHA-256，不便算哈希时记"版本号 + 打包时间"两格；服务形态记 `06` §9.6 的
   `releases/<ver>/` 版本号与当时的当前指向）。
四件各自的理由——冻结三类缺陷为何只在制品现身、为何换 `session_id` 那条负例要求副本与生产同构、为何只写版本号认不出是哪一次打包——
逐条写在 [`docs/delivery-checklist.md`](docs/delivery-checklist.md) B2，此处不复述。

**验收与交付确认。** 逐条填 [`docs/delivery-checklist.md`](docs/delivery-checklist.md)（选了路线②③④ 的，B3 段与服务侧那三条同等必过），
向用户说明产物位置、用法、退出方式，
并附上第 ⑦ 步的测试证据**与六条发布基线**（Golden 分维度通过率、典型任务估算成本、首字/整轮延迟 p50·p95、实际开放工具面宽与
每轮工具面 token、审批批准率与回滚率、门禁结果；口径见
[`references/21-operations-and-degradation.md`](references/21-operations-and-degradation.md) §6）——留了这组数字，下一次发版才有
"退化"可言，否则每次都是自说自话。
第 ① 步验收表的每一行都要指得出一次**制品上**的演示记录（谁看的、哪一天、看到什么），记在交付清单 B2；
这一趟**可以由该行的确认人本人执行并签名**：第 ① 步要求确认来自业务方而不是开发自查，而业务方在制品上亲眼跑过这一行，比读文字更强。
这一轮**任一条不过就停在第 ⑧ 步**，且改哪一侧决定哪些格子作废：改源码 → 制品重打，这一轮的演示记录与指纹全部重取；
改验收表那一行或改用例期望 → 第 ① 步那一行的确认人与确认日期同时作废，要回去重取背书（`19` §7 第 7 张第三条）；
只改环境配置 → 差异登记表补一行并写明重跑结果，演示记录可不重取，但要在那一行指到新的配置取值。
漏掉指纹登记的后果就是"改完顺手重跑一次就算过"，而重跑的那一份已经不是被验过的那一份了。
禁止技能与交付文档里出现机器专属绝对路径、兄弟技能名、外部业务项目名，都会毁掉可外发性与跨机复现（R12）。

**发出去之后要过观察窗，交付不是本步的出口。** 四格在发布前写定，随交付说明与六条基线存在同一处（事后补写等于没写过）：
① **放量批次**（新能力先对最小的入口 / 角色 / 账套集合开放；单文件自用形态换成「先在一台机器上跑满一个业务周期再分发」，不留空当作不适用）
② **窗口时长与看哪几条**（时长下限是覆盖一次完整的业务周期——月末结账的系统要跨到月末，不是统一"上线一周"；窗内只看第 ② 步回归半径
   对应的那几条基线加 `21` §2 的失败分类日志）
③ **回滚触发判据事先写死**四类（写面「写后回读不一致」线上出现即退 / 禁止面被命中或数据范围渗入一次即退 / 回滚率 > 0 不得放量 /
   成本与延迟相对上一版的劣化幅度自定一个百分数并写明）
④ **收口**（无触发 → 本期结项，按本步末拍那一页归档；有触发 → 按 `20` §6 四类归因回第 ⑦ 步重取证，口径本身变了则回第 ① 步重取背书）。
各格为什么必须事先写死（出事时会先争「这算不算严重」，回退的时机就在争论里过去）与逐条勾法见交付清单 B2 末段；
取数口径与阈值算法归 [`references/21-operations-and-degradation.md`](references/21-operations-and-degradation.md) §6。

**窗收口时写一页「本期停在哪里」。** 这一页不在本步的出口判据里：本步的出口是"发出去"，它的时点是"窗收口"，提前写就成了猜。四格：
① **做到哪儿**——第 ① 步验收表逐行给终态（已验并指到那一次演示记录 / 推到下期并写给谁、什么时候 / 主动不做并写明理由；
   三种取值都要有落点，空白行会被下一任读者读成"还没做"，而它实际可能是"决定不做"）
② **停在哪儿**——本期主动划出的边界连同理由（面表上故意不开的格、写侧作用域按哪种方式定的、观察窗阈值为什么留在那个值），
   每条回指一句业务事实或第 ② 步的某条约束；回指不到的那格正是最该留给后来人看的
③ **没清完的**——落成第 ② 步第 6 条约定那一处的单、逐条带号，禁止只写在这页上（一页纸会被删，一张单会自己出现在下一次开工的清单里）
④ **运营节奏归谁**——`21` §7 那三条（每周归因、每月看基线趋势、每季度用例集健康评审）逐条写人名，答不出就写"无人"。
**归档三样**：这一页、六条基线（`21` §6）、最后一次的制品指纹与演示记录，放在交付物旁边（同一个 `releases/<ver>/` 或同一份交付说明的附录）。
逐格的为什么与勾法见交付清单 B2 末段。本技能的交付边界到本期为止：这一页供后来人回看，但不构成下一期的开工前提，
禁止在这里写"下期必须从本页出发"那类强制。


> 出口判据：`release_gate`（及三系统门禁，如适用）全绿 + 交付清单已填 + 六条基线数字已存档 + 用户确认收到测试证据 +
> **观察窗四格（放量批次 / 窗口时长与看哪几条 / 回滚触发判据 / 收口留痕）已写定并随交付说明存档**（第 ⑦ 步的全绿说的是「当时那一份、那一次跑过」，观察窗才回答「这一版在真实业务里站住了没有」）+
> **验收表每行都有制品上的演示记录（含所验制品的指纹）、验收环境的差异已逐格登记、这一轮的作废传播已照上面处理**
> （这三条在源码上验多少次也补不齐，因为它们问的是"这一份制品、在这个环境"）；
> **选了路线②③④ 的**，再加上面那三条服务侧验收（重启自恢复 / 真实回滚演练 / 多客户端不串台）——缺一条就是"能起但守不住"。

## 〔回路〕上线后回流（非步骤；按节奏重复）

上线不是终点。把线上错答变成下一条回归用例，系统才随使用变好而不是随使用腐化。
**刚发出去那一段不归本回路，归第 ⑧ 步写定的观察窗**：那里判的是「要不要回退」，本回路改的是「要不要改用例」；
窗收口时要写的那一页（做到哪儿 / 停在哪儿 / 没清完的 / 运营节奏归谁）见第 ⑧ 步末拍，窗收口之后下面的节奏才是常态。回路不是步骤，**它回到入场检查与第 ① 步**：

采（`21` §2.1 字段 + 用户纠正动作，一次点击即可；**采到的那一条当场落成第 ② 步第 6 条约定那一处的一条单，禁止只停在聊天框里**
——留在对话里的反馈没有一个可回指的号，后面归因、复现、签认全都接不上）→
归因（按 `20` §6 四类分：契约漂移 / 装配故障 / 模型波动 / 业务真变化）→
沉淀（脱敏后入 Golden 集，`20` §4.1 第三来源，同一次提交带修复、且提交信息带那张单的号；
口径、权限或数据源权威真的变了，则先回第 ① 步改契约表，再改用例期望）→
回归（`20` §4.4 各段 + `21` §6 基线对比）→ 再交付（第 ⑧ 步门禁）。

用量与成本走 `agent.usage_pricing` 统一口径估算并在界面标注"估算"（禁止显示成真实费用，R7）；
失败必须分类记日志，禁止一律 `"error"`。节奏建议：每周批量归因一次（不建议逐条即时反应），每月看一次基线趋势，
每季度做一次用例集健康评审（`20` §5 的淘汰与补入成对发生）。
**回到入场检查的触发条件**：用户升级 `hermes-agent`，或你回头改本技能——跑漂移四线，必要时 `--regenerate-apiref`，
把「官方文档说 A、源码是 B」的结论沉淀回 [`docs/troubleshooting.md`](docs/troubleshooting.md) 与基线文件。
Hermes 自身会沉淀记忆与技能（`08`、`13` §2.2），但记忆后端只允许一个外部 provider（`13` §2.2），禁止两个后端并存、各自返回不一致的记忆。

完整 13 条反模式红线（含各自的适用路线）汇总在 [`references/07-quality-gates.md`](references/07-quality-gates.md) §1，
全局索引与各文档适用路线标注在 [`references/00-index.md`](references/00-index.md)；变更记录见 [`CHANGELOG.md`](CHANGELOG.md)。
