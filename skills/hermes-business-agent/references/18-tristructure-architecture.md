# 18 · 三系统解耦架构（高内聚低耦合的工程级落地）

> 本文件回答一个问题：**当业务是一个完整系统（需独立交付、长期演进、底座可整体替换）时，如何组织 Hermes 集成工程，使系统达到高内聚、低耦合。**
> 它把「高内聚低耦合」从**进程内分层**（§8 的 GUI/桥接/Agent 四层）提升到**工程组织层面**（三个独立系统），并进一步落到**各系统内部功能模块**。
> 适用前提：你的业务已超过"给单个桌面应用加个 AI 面板"的规模，需要独立的业务工程、可替换的 Agent 底座、明确的桥接层。
> 参考落地：`examples/01-hermes-desktop` 的三系统骨架（`业务系统` / `连接系统` / `Agent系统`）。

---

## 1. 为什么需要工程级分层

「单工程内嵌」范式（复制 `examples/01-hermes-desktop` → 在同一个工程里加业务 + Agent）适用于中小型应用。当业务演化成完整系统时，会出现：

- **业务与底座深度耦合**：业务代码 import 底座内部模块（`server`/`routes`/`agent_runtime`…），底座升级换代时业务被拖累，反之业务膨胀污染底座纯净性。
- **单一职责缺失**：一个工程同时是"业务系统"又是"Agent 系统"，职责不清、边界模糊、演进互相拖累。
- **无法独立演进/交付**：业务无法独立打包分发，Agent 底座无法整体替换，两者必须绑定发布。
- **模块内聚下降**：业务逻辑散落各处、copy-paste 泛滥、死代码堆积，难以维护。

**三系统解耦架构**针对上述问题，把工程拆成三个职责单一、依赖单向、接口稳定的独立系统。
下表按**建工程的顺序**列（先有纯业务，再抽桥接，最后才是可替换的底座），依赖方向与它相反，见 §2.1：

| 系统 | 职责 | 关键约束 |
|---|---|---|
| **业务系统** | 纯业务逻辑与界面，不依赖 Agent | 可独立运行/独立 EXE；不 `import` 任何 Agent 模块 |
| **连接系统** | 纯桥接，唯一装配耦合点 | 负责把业务挂到 Agent、注册工具、注入快照、安装技能 |
| **Agent系统** | 纯净 Hermes 底座（= `examples/01-hermes-desktop`，零差异） | 可整体替换；不含业务 |

## 2. 高内聚低耦合的两层落地

### 2.1 系统间（宏观层）：依赖方向铁律

```
业务系统 ──► 连接系统 ──► Agent系统
   │            │            │
   │    (唯一装配耦合点)      │
   └──── 绝不直接 import Agent 模块 ──┘
```

- **单向依赖**：业务系统 → 连接系统 → Agent系统。**业务系统禁止 `import` Agent 系统任何模块**（`server`/`routes`/`agent_runtime`/`tools`/`hermes_config`…）。
- **连接系统是唯一装配点**：所有「业务 ↔ Agent」的桥接（挂业务路由、注册 rd 工具、注入业务快照、安装技能）全部收拢在连接系统的装配函数里（如 `fuse_business_into_agent()`）。
- **Agent系统可整体替换**：它是上游 `examples/01-hermes-desktop` 的纯净副本，无业务痕迹；升级底座只需「删除→复制→粘贴」三步，业务/连接不动。
- **稳定接口**：三个系统通过**明确的函数接口**协作，不依赖对方的内部实现细节：
  - 业务系统暴露纯业务接口：`build_app()`（自建 app）、`mount_rd_routes(app, rt)`（挂业务路由）、`get_business_snapshot()`（业务快照）。
  - 连接系统暴露装配接口：`fuse_business_into_agent()`（返回融合 app）。
  - Agent系统暴露底座接口：`server.app/rt`、`agent_runtime`、`tools.registry`、`routes.chat`。

### 2.2 系统内部模块间（微观层）：单一职责 + 模块内聚

高内聚低耦合不只存在于三大系统之间，更要求**每个系统内部的模块**同样遵循。三系统只是把内聚边界放大了，内部的模块设计原则不变：

- **单一职责**：一个模块只做一件事。路由模块（`routes_*.py`）只负责页面/接口，不塞 Agent 逻辑；桥接模块只负责装配。
- **模块分层**：GUI/渲染层、桥接层（callback→queue）、Agent 构造层、工具层、数据层分层清晰，不跨层调用。
- **共享抽取**：跨模块重复的辅助逻辑（下拉选项、统计块、表格渲染、端口探测等）抽到公共模块（`components.py`/`helpers.py`），**消除 copy-paste**。
- **禁止死代码**：未被引用的模块、函数、import 一律清理。注意本技能的六道门禁里没有这一项（`py_compile` 只报语法错，
  看不出未使用引用），须由业务侧自装静态检查器（如 `pyflakes`、`ruff check`）跑一遍作为佐证，它不是交付门禁。
- **公共依赖归位**：Agent 使用的业务技能（SKILL）不放在业务系统，而归入连接系统，由连接系统在装配时安装给 Agent。
- **独立入口**：每个系统有自己的一键启动（`启动.bat`）和独立打包（EXE），互不依赖。
### 2.3 开工前要写下的组织约束（第 ② 步第 1–5 条的落地细则）

SKILL.md 第 ② 步要求六条组织约束在开工前落成文字，那里只留题目与出口判据，细则在本节——归本节是因为六条里五条约束的是
"模块与目录怎么摆"，正是本篇 §2.1（系统间）与 §2.2（系统内）要解决的问题；第 6 条（改动进仓与签认）不在这里，见 `20` §5.1。

- **目录与依赖方向**：单工程内嵌按功能域先划四层——GUI/渲染、桥接（callback→queue）、Agent 构造、工具，四层不混；
  三系统分离直接建 `业务系统/` `连接系统/` `Agent系统/`，并按 §2.1 把依赖铁律写进 README。系统内部同样按功能域拆包，
  路由/服务/桥接/数据/工具不跨层调用（§2.2）。
- **Agent 集成代码独立成模块**（如 `agent_runtime.py`），禁止塞进路由文件：桥接逻辑的边界在这一步用目录划出来，不靠事后重构。
- **工具函数的实现口径**：纯 Python 实现，不要 shell 调用外部命令绕过工具面——绕过去的那一步不在面上，第 ⑥ 步的闸门与
  第 ⑦ 步的断言都看不见它。要返回结构化结论的，字段级 schema 的归属模块在本步定（如 `schemas.py`），
  第 ⑤ 步 `complete_structured` 与第 ⑦ 步断言共用同一份（细则见 `20` §1）。
- **规模与外发红线**：单文件过大即拆；共享辅助抽进 `_utils.py`（既消 §2.2 的 copy-paste，也防拆包后的循环导入），
  拆包时 `__init__.py` 重导出保向后兼容；死代码（未引用的模块/函数/import）随手清，`pyflakes` 或 `ruff check` 佐证。
  文档与代码里不落机器专属绝对路径、不引兄弟技能名、不写外部业务项目名（R12，`07` §1）——
  交付物能单独外发、跨机复现全靠这几条早约定，越晚补代价越大。
- **回归半径与回退方式，各写一句话**。第一句写明本次改动会碰到哪些既有功能与数据：第 ⑦ 步那条「覆盖宿主系统原有功能用例」
  要跑哪些用例由它决定；不在此写明，回归范围就要到第 ⑦ 步写用例时才现场确定，漏掉的那一部分没有别的环节会补。
  第二句写明上线后出错退回到哪里，三种回退方式选一或并列——**制品回退**（保留上一版可执行文件）、
  **数据回退**（本次写操作能否撤销、按什么键回滚）、**配置回退**（把某个开关或阈值改回原值即可停用新能力）。
  每一种都要写明执行入口（命令、界面按钮或流程编号）。本句只管「有没有可执行的入口」，**什么信号出现才退**留给第 ⑧ 步
  观察窗写定（`SKILL.md` 第 ⑧ 步与 `21` §6）：前者开工前就答得出，后者要等量出基线才有阈值可写。
  单机形态同样需要第二句：`06` §9.6 的回滚六步只适用于常驻服务，单文件制品的回退就是换一次可执行文件。

## 3. 三系统架构总览

```
                        ┌───────────────┐
                        │   业务系统     │  build_app() / mount_rd_routes() / get_business_snapshot()
                        │  (纯业务+UI)   │  独立 EXE、独立启动
                        └───────┬───────┘
                                │ 纯业务接口（不 import Agent）
                                ▼
                        ┌───────────────┐
                        │   连接系统     │  fuse_business_into_agent()
                        │  (纯桥接)     │  ├ 挂业务路由到 Agent app
                        │              │  ├ 注册 rd 工具到 tools.registry
                        │              │  ├ 注入业务快照到 routes.chat
                        │              │  └ 安装业务技能到 HERMES_HOME/skills
                        └───────┬───────┘
                                │ 稳定底座接口
                                ▼
                        ┌───────────────┐
                        │   Agent系统    │  server.app/rt · agent_runtime · tools.registry
                        │  (=01 纯净底座)│  = 上游 example01 零差异，可整体替换
                        └───────────────┘
```

**融合装配流程**（连接系统 `fuse_business_into_agent()`）：
0. **组装 `sys.path`：必须包含 `Agent系统/` 本身**（底座代码在三系统根下的 `Agent系统/`，不是三系统根）。
   这一步的清单只留一处（`bridge.ensure_syspath()`），入口 `main.py` 不重复维护——两份清单各写一遍是三系统最典型的漂移源。
1. 从 Agent系统导入 `server.app` / `server.rt`
2. 调业务系统 `mount_rd_routes(app, rt)` 把业务路由挂到 Agent app
3. 把业务 `get_business_snapshot` 设为 Agent 底座 `routes.chat` 的 `BUSINESS_CONTEXT_HOOK`
4. 注册业务工具到 `tools.registry`、安装业务技能到 `HERMES_HOME/skills`
5. 包装 `stream_agent_chat` 使 Agent 对话感知业务数据
6. 返回「Agent 对话 + 业务路由」融合 app

> **装配失败不许静默回退**：`except` 里回退成纯业务 app 会得到一个"照样 200、但里面根本没有 Agent 对话"的
> 假绿产物（实测：`from server import` 因缺 `Agent系统/` 入 path 而 `ModuleNotFoundError`，页面照常起）。
> 底座目录整体缺失 → 返回 `None` 让入口直接失败；确实要降级 → 日志必须打出醒目 禁止，
> 且**融合成功的唯一判据是日志出现「融合装配完成」**，禁止用 HTTP 200 当装配证据。
> 详见 `docs/troubleshooting.md` §10 与 `release_gate.py --verify-launch`。

## 4. 决策判据：单工程内嵌 vs 三系统分离

| 判据 | 单工程内嵌（默认） | 三系统分离 |
|---|---|---|
| 业务规模 | 中小型、单一应用 | 完整业务系统、多模块 |
| 独立交付 | 一个 EXE 即可 | 业务需独立打包分发 |
| 底座可替换 | 不关心 | 需频繁/自主升级底座 |
| 业务与 Agent 耦合 | 可接受 | 必须彻底解耦 |
| 长期演进 | 快速迭代小应用 | 多团队/多生命周期演进 |
| 复杂度代价 | 低 | 高（三目录 + 装配层 + 验证） |

> **默认走单工程内嵌**；当业务已具备"完整系统"特征（多模块、需独立交付、底座需可替换、业务与 Agent 解耦是硬约束）时，升级为三系统分离。


### 4.1 调用路线 × 工程形态的合法组合（第 ② 步定形时的自洽判据）

工程形态这一件不能单独定：**它以"进程边界"为分界**，要与第 ② 步选定的调用路线逐格配对。

| 调用路线 | 单工程内嵌 | 三系统分离 |
|---|---|---|
| ① 进程内直跑 | 合法（中小型应用的默认） | **合法**：`连接系统/` 就是那个进程内的唯一装配点，`fuse_business_into_agent()` 成立（旗舰参考实现即此形态） |
| ② 网关 / ③ spawn CLI / ④ API Server / ⑤ `/v1`（跨进程） | 合法（需自建薄层） | **受限**：`连接系统/` 的职责变成网络服务与协议桥（鉴权、会话头、序列化都压在它身上），"在同一进程内把业务装配进 Agent"的范式不再成立 |

- 跨进程路线 + 三系统骨架这一格禁止硬凑：不要把三系统目录原样搬上跨进程路线、再在装配函数里塞 HTTP。要么按该路线自身的形态组织（网关见 `16`、服务端见 `15`），要么退回单工程内嵌并自建薄层。
- "三系统分离"配 spawn CLI 或仅 `/v1`，只在业务侧确实需要独立分发与可替换底座时才合法，否则无谓多付一层目录成本。
- 两件定不拢时以**交付形态**优先：先满足"用户从哪进来"（部署入口那一问），工程形态随后跟上。但能力入口那一问不能靠这一句回避——它必须落成配置行（`19` §7 第 6 张），否则就是多处入口、权限有多处要各管一遍。

## 5. 落地步骤（在 examples/01-hermes-desktop 底座上搭三系统）

1. **建目录**：把 `examples/01-hermes-desktop` 复制为 `Agent系统/`（保持零差异）；新增 `业务系统/`、`连接系统/`。
2. **业务系统**：从你的业务抽离出纯业务 app（`build_app()` 自建、`mount_rd_routes()` 挂路由、`get_business_snapshot()` 出快照），**确保不 import 任何 Agent 模块**；配独立 `启动.bat` 与独立 EXE 打包。
3. **连接系统**：新建 `bridge.py`，实现 `fuse_business_into_agent()`（见 §3 装配流程）；入口 `main.py` 调装配函数得到融合 app 后启动 uvicorn + pywebview。
4. **Agent系统**：保持 = `examples/01-hermes-desktop` 纯净底座，写 `替换Agent系统.md` 说明三步替换法。
5. **验证**：跑 §7 三系统验证门禁，确认融合/独立双模式都正常。

## 6. 底座替换三步法（Agent系统可整体替换）

```
① 隔离运行时数据 → 备份并移除旧 Agent系统目录
② 以纯净底座重建 Agent系统（submodule 升级 / 整仓 clone 上游）
③ 回填数据 → 跑门禁 → 融合/独立双模式冒烟
```

> 前提：业务/连接只通过 §2.1 的稳定接口依赖 Agent，不 import 其内部模块；Agent系统保持零差异、无业务痕迹。
> **坑（必须写进交付件的 `替换Agent系统.md`）**：开发态 `HERMES_HOME` 就是
> `Agent系统/hermes_config/.hermes_data/`，**在底座目录内**——直接删目录等于删用户数据。
> 冻结态则是 `<exe>/hermes_data`（在代码外，换代码不动数据）。
> 用 `HERMES_DESKTOP_HOME` 把数据根外置后，替换才真正退化为「只换代码」。
> 完整可执行版本（含命令、回滚、与上游 breaking change 的分界）见
> `examples/01-hermes-desktop/替换Agent系统.md`。

## 7. 三系统验证门禁（交付前必跑）

一条命令，六项硬门禁 + 一项软门禁；未启用三系统骨架时整体报 SKIP 不阻断：

```bash
python scripts/verify_tristructure.py --root <三系统根>      # CI 加 --strict：软门禁 SKIP 也算失败
```

| 检查 | 类型 | 断言（脚本实际做的事） |
|---|---|---|
| `structure_ok` | 硬 | `业务系统/` + `连接系统/` + `Agent系统/`（或 `替换Agent系统.md`）在位 |
| `biz_no_agent_import` | 硬 | 业务系统全部 `.py` 的顶层 import 不落在 Agent 模块集（`server`/`routes`/`agent_runtime`/`hermes_*`…） |
| `conn_unique_assembly` | 硬 | 只扫 `业务系统/` 与 `连接系统/` 两个目录下的 `.py`（正则 `^\s*from\s+server\s+import`），断言**业务系统内零命中**，连接系统是允许的那一处。"唯一"到此为止：Agent 系统与根目录不在扫描范围内，故它查的是"业务侧不自行装配"，不查全仓装配点散落；命中文件会全部列出供人工看。同一思路用于业务侧配置表：入口表/面表的 loader 也要单点，查法见 `19` §6 第 6 条 |
| `biz_independent_entry` | 硬 | 业务系统有独立入口：`app.py` + `启动.bat` |
| `agent_purity` | 硬 | 三系统根的顶层条目无业务痕迹（无业务模块名/业务技能目录） |
| `agent_zero_diff` | **软** | 见下方语义边界 |
| `replace_doc` | 硬 | `替换Agent系统.md` 在位（底座不可安全替换 = 交付缺陷） |
| 融合装配 | 人工/冒烟 | `fuse_business_into_agent()` 后业务路由 + Agent 对话 `/api/chat` 双 200 |
| 独立运行 | 人工/冒烟 | 业务系统独立启动，业务路由 200（无 Agent 对话端点，符合预期） |
| 无死代码 | 无门禁 | `quality_check.py` 的六段里没有这项（`py_compile` 只报语法错）；未使用 import / 未引用模块要靠业务侧自装的静态检查器（`pyflakes`、`ruff check`）人工跑，结果不作为交付凭据 |

> **`agent_zero_diff` 的语义边界**（别误读绿色）：它用
> `git status --porcelain --untracked-files=no` 断言底座**未被本地改动**，并打印 `HEAD` 短 sha 供人工比对。
> 它**不联网**，因此**不证明"与上游最新一致"**——底座停在旧版本但本地干净同样 PASS；
> 要监测上游漂移用 `scripts/track_upstream.py`。
> **降级路径**（四类情形判 SKIP，不阻断；`--strict` 下才计失败）：
> ① 无 `Agent系统/` 目录（单工程内嵌形态本无此概念）；② `Agent系统/` 非 git 仓库或 submodule 未初始化
> （提示 `git submodule update --init`）；③ `git` 命令不可用（离线/未装）；④ `git status` 执行失败。
> SKIP 时打印的原因文本即为待办事项，不要靠删检查项让它变绿。
> 「软」仅指这四类取不到证据的情形；git 可用且查出底座有本地改动时它是 FAIL 且阻断，
> 此时唯一正确的处置是撤回改动、改动走上游 PR（见 §6）。

## 8. 反模式红线（禁止）

- **禁止** 业务系统 `import` Agent 模块（`server`/`routes`/`agent_runtime`/`tools`）——耦合，破坏独立性。
- **禁止** 业务逻辑散落 / copy-paste 重复辅助函数 —— 破坏模块内聚，应抽公共模块。
- **禁止** Agent系统被业务污染（塞业务代码/业务技能）——破坏可替换性。
- **禁止** 装配逻辑散落多个系统 —— 应全部收拢到连接系统唯一装配函数。
- **禁止** 留着未引用的模块、函数或 import 不清理 —— 堆积僵尸代码，难以维护（这一项无门禁，见 §2.2）。
