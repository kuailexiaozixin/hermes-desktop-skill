# 20 · 业务输出契约与 Golden 数据集

> **适用路线**：全路线（②/④ 路线的 schema 归属服务端；①/③/⑤ 归属宿主进程）。
> **主线位置**：SKILL.md 第 ① 步（定 schema 归属模块）、第 ⑤ 步（产出结构化结论 + 随工具建用例）、第 ⑦ 步（跑 Golden 回归）。
> **与其它参考的分工**：`01` §3.4/§3.4bis = 透传通道与结构化输出的**API**；`02` §12 = `ctx.llm` 宿主推理机制；
> `09` §8 = LLM Judge 三段式**评估方法**；`19` §7 = 契约表（本文把它变成可回归的测试资产）。
> 本文管两件事：**业务要的字段级结论怎么定契约**，以及**这条契约怎么被一组用得起来、改得动的 Golden 用例锁住**。

## 本文的读法：六节是一条依赖链，不是六个专题

**先定契约（§1）→ 再把字段设计成模型填得对的形状（§2）→ 再排校验顺序（§3）→ 才派得出用例（§4，派之前先按「归属」选轨）→ 用例靠维护活着（§5）→ 跑挂了先归因（§6）**。
链上有两处硬依赖，倒过来做必然返工：§4 的每条用例都是从 §1 的 schema 和 §3 的校验点**派生**出来的，
禁止先攒一堆"问一句看回答"的用例再回头补契约（那种用例断言的是散文，改一次文案就全红）；
§6 的归因分类也只有在前五节都已确定之后才有意义（分不出"契约漂移"还是"模型波动"，通常是 §1 的三件套缺一件）。
§7 的反模式不独立成流程，它是前面六节各自的"做错时的样子"，读回对应节即可。

## 1. 输出契约三件套（缺一件就是没契约）

任何"要进业务系统的结论"都必须同时具备三件，缺一件就退化成"读一段人话再猜"：

| 件 | 要求 | 落点 |
| --- | --- | --- |
| **schema** | 字段名、类型、枚举、单位、可空语义全部显式；带 `schema_version` | 独立模块（如 `schemas.py`），第 ① 步就定归属，禁止散在路由/提示词里 |
| **校验点** | 模型输出先过 schema 校验，再过业务不变量校验，才允许落库 | 工具 handler 或调用方，两处都不许省 |
| **消费方** | 明确谁读它：入库字段 / 界面渲染 / 下游函数入参 | 契约表（`19` §7 第 5 张）只有"业务动作 → schema 名 → 归属模块"三格，消费方要在同一张表上补一列逐 schema 记名 |

## 2. schema 设计规则（面向模型的字段设计）

模型填不好的字段，多数是设计问题不是模型问题。

- **枚举显式**：状态类字段给 `enum`，不要写成"字符串，例如已完成"。
- **单位入名**：`amount_yuan` / `qty_pieces` / `due_at_iso8601`，禁止裸 `amount`（含税/单位靠运气）。
- **可空有语义**：区分"业务上不存在"与"本次没查到"。要么给 `missing_reason` 枚举，要么规定 `null` 的唯一含义，并在断言里锁住。
- **禁止自由长文本**：需要解释就单独字段并给长度上限（`summary: str ≤120 字`），禁止让结论与解释混在一段话里——那是不可断言的形状。
- **数组给上限**：`items: list[...] (≤20)`，并在 handler 里真裁，别只写在描述里。
- **一次动作一个 schema**：禁止把一个"万能结果"schema 塞满可选字段（模型倾向全填或全不填，断言无从下手）。
- **带版本**：`schema_version: "v1"`；字段改名走 §5 的双写窗口，禁止直接改语义。

## 3. 校验落点（模型输出默认不可信）

两条原生路径，机制见 `01` §3.4bis 与 `02` §12，本文只定顺序：

```python
# 插件内用宿主推理拿强类型结论（API: PluginLlm.complete_structured，结果在 .parsed）
res = ctx.llm.complete_structured(
    instructions="从订单文本提取关键字段",
    input=[PluginLlmTextInput(text=raw)],
    json_schema=ORDER_FIELDS_V1,          # 有界强类型：传 schema 时会做校验
)
order = OrderFields.model_validate(res.parsed)   # ② 业务侧二次校验（pydantic/dataclass）
assert_invariants(order)                          # ③ 业务不变量：金额≥0、状态机合法、范围合法
persist(order)                                    # ④ 才允许落库/渲染
assert readback(order) == order                   # ⑤ 写面：回读实际生效值再认账（`19` §3）
```

- ① `json_schema` 让 Hermes 侧解析与校验（`json_mode=True` 走宽松模式，能不用就不用）；
- ② **不能省**：模型可能给出类型合法但业务非法的值（未来日期、不属于本账套的客户号）；
- ③ 校验函数与 `19` §7 第 4 张「不变量表」同源，一条不变量对应一个断言函数，两边共享；
- ④ 校验失败的处置是**回到界面要求人工确认或重问**，禁止静默重试到"看起来对了"为止（成本与假绿双杀）。
- ⑤ **只有写面必做**：`persist` 成功不等于业务生效（可能被状态机回退、被审批改值、被下游规则覆盖）。
  回读口径以业务系统真值为准，禁止把"接口返回 200"当"已生效"——那是假绿最常见的形态。
- 纯对话侧要稳定格式，走 `request_overrides` 透传（`01` §3.4），但透传只保证格式，不保证语义——②③ 照样要做。

## 4. Golden 数据集（从哪来、多少条、怎么维护）

### 4.1 三个来源（缺一不可）

| 来源 | 说明 | 占比建议 |
| --- | --- | --- |
| **真实历史单据** | 从既有业务数据里抽已发生过的输入与已知的正确结论 | ≥ 一半（贴近真实分布） |
| **业务专家出题** | 让业务人员写"这种问法应该得到什么"，尤其是不变量与边界 | 三到四成（补覆盖盲区） |
| **线上失败样本回流** | 运营期发现的错答、越权尝试、降级路径，脱敏后入集 | 持续累积（见 `21` §7） |

### 4.2 规模基线（先有能用的一组，再谈趋势）

- **结构基线**（下面的"每格几条"是本节定的数，`19` 只负责给出要被覆盖的格子）：面表（`19` §7 第 1 张）每个工具
  ≥ 3 条正常 + 2 条负例（越权/无效入参）+ 2 条边界（空集、超大、跨期）；权限矩阵每格 ≥ 1 条；
  不变量表（`19` §7 第 4 张）每条 ≥ 1 条断言用例。
- **维度**：四类基本维度（只读面 / 受控写面 / 越权负例 / 降级）之外，另立两类必测负例——
  **多源冲突**（同一事实两个来源给两个数，断言按 `19` §2 的权威源取、且把误差说出来）与
  **写后回读不一致**（stub 一个"接口成功但值未生效"的响应，断言系统报不一致而不是报成功）。
- **量级**：**30–50 条即可上线做回归**（够抓明显退化）；**100+ 条才开始有质量趋势可言**，200+ 才值得设阈值门槛。
  用例数低于 30 时不要设"通过率红线"——随机性会淹没信号，改用人人过一遍的评审。
- 不许用"我手工问了十个问题都对"代替入集用例。手工验一遍等于没验。

### 4.3 一条用例的形状

```python
GOLDEN = [
    {
        "id": "G-ORD-004",
        "prompt": "帮我看下华东账套上月未结清的订单里金额最大的三笔",
        "context": {"role": "sales_east", "ledger": "EC-2026-07"},   # 主体与范围，来自 19 §2
        "behavior": ["query_orders"],                                  # 期望被触发的工具（行为契约）
        "forbidden": ["export_all", "terminal"],                        # 期望缺席的工具/动作
        "fields": {"count": 3, "amount_yuan_positive": True,           # 值/谓词断言，不比文本
                   "ledger_in_scope": "EC-2026-07"},
         "invariants": ["no_cross_ledger", "settled_immutable"],         # 引用 §3 的断言函数名
        "readback": True,                                            # 写面用例：必须回读实际生效值再判过
        "source": "历史单据",
    },
]
```

要点（与 `09` §3 Step 5b 的宿主原有功能用例同一口径）：断言**行为与字段**，禁止比对回答文本；
`forbidden` 与 `invariants` 是业务智能体最值钱的两类用例——它们防的是"自信地做错"。

**这份形状同时是机检的读取接口**（`scripts/check_golden_coverage.py`，SKILL.md 第 ⑤⑦ 步那道对账门按它解析用例集），
所以三条约束是硬的：

1. 用例集必须是**静态字面量列表**（默认变量名 `GOLDEN`；JSON 文件则根节点为数组，或 `{"GOLDEN": [...]}`）。
   用循环或推导式生成的用例集它读不出，这是刻意的：生成器改一次规则会同时改掉整批期望值，
   那正是 §6 禁止的「失败就改用例期望去过」的批量形态——批量到没有人会去逐条复核。
2. 每条 `id` 必须登记进 `19` §7 第 7 张的「派生的 Golden 用例编号」列，且形状是**以字母开头的单个 token**
   （`G-ORD-004` 这种；列内多个编号只用顿号/逗号/分号/斜杠/空白分隔）。表头列名与 id 形状是脚本认表、取值的唯一依据，
   只改文档那一侧的列名会让对账找不到表、把相关各条判失败（它不静默跳过，见 `19` §7 末尾那条声明），
   所以改名必须两处同改。
3. 值断言不许写成占位词（`"count": "非空"`），占位词等于没断言，对账直接判失败。

对账查不到的三件事，不要把它当回归：用例是否真的跑过（它不执行）、期望值对不对（根据是验收表那行的业务原话，
机检只核有没有回指；这一格只能由评审认定：改过期望值的提交必须换人签，判据在 SKILL.md 第 ② 步第 6 条与第 ⑤ 步）、
正例/负例/边界配比够不够（一条用例属于哪一类无法从字段派生，故只提示不阻断）。

### 4.4 运行位置与判定

- 静态对账段（无 Key、不执行用例）：`scripts/check_golden_coverage.py`，核用例集与契约表（`19` §7 第 1、7 张）互相指认得通不通；
  它是 §4.3 那三条约束的执行处，运行位置在 SKILL.md 第 ⑤ 步（每加一个工具）与第 ⑦ 步（跑回归之前）。
- 离线确定性段（无网络）：`09` §9 的 mock 回放 + `test_bridge.py` 桥接断言，只验形状与装配，禁止在此段验语义质量。
- 真实 LLM 段（有 Key，交付前由用户跑）：`09` §3 Step 3 收集事件流、Step 4 断言终态 `done`、`len(deltas) > 0`、
  `action` 与 `action_result` 数量相等（断言表 A3–A5）。"回调是否接得上"不在这段，它是 Step 1 `runtime_ready()` 的签名检查
  （四个构造回调在位 + `run_conversation` 有 `stream_callback` 形参，代码见 `07` §3）。
- 语义打分段：`09` §8 LLM Judge 三段式（判官也用 `complete_structured` + 强类型结果，落库可比对）。
  判官分**只做趋势与筛疑**，禁止当放行开关；放行开关只能是字段/行为断言。
- 判定口径：同一组用例连跑取稳定通过率（≥3 次），阈值设在稳定值之下，防抖动误阻断。
- 以上各段跑的对象都是**源码/开发环境**。交付前还要在**制品**上把本期验收表覆盖到的那几条重跑一遍，
  且在与生产隔开的环境里跑——判据与理由在 SKILL.md 第 ⑧ 步的验收前置事项，本节只登记这一格不重复写。

### 4.5 先按「归属」选轨，再按 §4.4 选运行位置

§4.4 那几段说的是**在哪跑**，它回答不了**该在哪条轨上断**。后者由 `19` §3 第 5 步面表里的「归属」列决定，
两轨混用最常见的两种错法：

- **判给代码的环节不得进 Golden 集**。确定性计算（含税换算、账期展开、状态可达性、聚合与格式化）走单元测试与离线断言：
  入参非法必拒、幂等重放不重复写、复算一致。拿 LLM 断言去测固定规则，除了慢和抖，最坏的是**真凶是代码 bug 时用例照样"通过"**——
  模型这一次碰巧复述了那条写错的规则，通过率把 bug 盖住了。
- **判给模型的环节不得用 mock 断行为**。mock 里模型不推理，断出来的"通过"与线上无关；这类环节只进 Golden 分维度
  （通过率口径见 `21` §6 第 1 条）。
- **两条轨的接缝单独留负例**：模型结论回代码过 §3 校验链时，"格式合法但业务不成立"的输入两边都不管——
  代码没做错（它照规矩拒了）、模型也可能一直不犯，只有这条负例守着。

> 一句话记法：**代码轨断"算得对不对"，模型轨断"判得稳不稳"，接缝轨断"拦得住拦不住"。**
> 面表里没有「归属」这一列，第 ⑦ 步就只能凭感觉给整条链套同一套测试。

## 5. 演进与维护（让用例集活得过三次需求变更）

| 变化 | 处置 |
| --- | --- |
| 新增业务工具 | **同一次提交**必须带 §4.2 基线量级的用例（用例在第 ⑤ 步随工具写，不是第 ⑦ 步现补）；这一条由 `scripts/check_golden_coverage.py` 在第 ⑤ 步逐工具核、第 ⑦ 步开跑前再核一遍（它查得到"面表有这一格、用例集里没有"，查不到期望值本身对不对） |
| 字段改名/换义 | 双写窗口一版：新旧字段同时产出，用例切新，契约表标注弃用，下一版删旧字段 |
| 提示词/模型变更 | 全量重跑；按 §6 分类失败原因后再决定回滚还是改用例基线 |
| 业务规则变更（不变量增删） | 先改 `19` §7 的不变量表（其内容出自 §2.2 问 5），再改断言函数，最后改用例期望；顺序反了会掩盖漏改 |
| 用例长期失效（业务实体已不存在） | 季度评审淘汰，但**必须补同覆盖的新例**，禁止只删不补（覆盖率会静默塌陷） |

> 用例集与业务代码同库、同 PR、同评审。禁止单独的"测试数据仓库"——它会立刻漂移。
> "同评审"落在哪一处、四件指什么、由谁签，细则在本节 §5.1；SKILL.md 第 ② 步第 6 条与第 ⑤ 步只留题目与出口判据。

### 5.1 改动进仓的单元与签认（第 ② 步第 6 条约定、第 ⑤ 步执行）

- **三样要在第 ② 步定完**：需求与缺陷记在哪一处（Issue、工单、表格都行，**只有聊天记录不行**——它没有一个可回指的号，
  后面归因、复现、签认全都接不上）、提交信息用什么形状回指它（`#123`、`ORD-45` 这类）、一次评审最少要看到什么才算可审。
  没有评审平台时的最低要求是一份变更台账，逐条带号。
- **一次评审要看见的四件**：handler 实现、该工具的 Golden 用例（量级见 §4.2）、面表上那一行、验收表「派生的 Golden 用例编号」
  那一格（`19` §7 第 7 张）。四件拆成两次提交，前一次交付的就是一个没有回归覆盖的能力；拆给两个人做，
  最后少的那一格通常是回指——它只对别人有用，不对写用例的人自己有用。第 ⑥ 步动过审批规则或工具面配置的那一版，
  附上当时的面 diff（`19` §6）一起送审。
- **改过期望值的那一批必须换人签**。它是这一拍里唯一机检让路的格子：§4.3 查得到"有没有回指"、查不到"期望值对不对"；
  而且它改得很安静——用例还是那条用例、id 还是那个 id，对账照样全绿。只改期望值而没人签就合进去，
  等于把第 ① 步业务方签过的那一行悄悄换成开发自己的判断。能签的人取自 `19` §7 第 7 张对应行的确认人本人或其指定的人；
  两类人都找不到时，期望值不改。
- **评审后的回写要闭环**：每条待改意见改完就在那一处回复并关闭，决定不改的写明理由留档，每次合入后同步更新那条记录的状态。
  禁止代码已合入、意见还挂着、记录上仍写着"待开发"——那一处的状态是下一次开工的起点，停在半成品就等于下一次先重新问一遍
  "这一条做完没有"，而答复又只落在聊天框里。
- **这道门仍可被跳过**：`scripts/check_golden_coverage.py` 是"愿意跑才跑"的命令。要让它跳不过去，只能把那一行命令挂进业务项目
  自己的 pre-commit / pre-push 钩子或流水线，非零退出即挡住推送——钩子属于那个仓库，本技能不代装；
  没挂钩子时，第 ⑤ 步的出口判据仍要靠人工核一遍。
- **留痕的用处是回放**：线上出错时按号走一遍（错答 → 用例 → 引入它的那次提交 → 当时谁签的），
  本期收口时也拿这串号当素材（`SKILL.md` 第 ⑧ 步末拍），不必事后重写一遍经过。

## 6. 失败分类（先分类，再决定改什么）

一条 Golden 失败，四种归因，处置完全不同：

1. **契约漂移**：字段名/枚举变了 → 改 schema 消费方或回滚（用例是对的）。
2. **装配故障**：工具没被调用、回调没触发、上下文缺段 → 修第 ④⑤ 步接线，禁止改用例期望（这是最容易造假绿的地方）。
3. **模型波动**：同输入偶发跑偏 → 加 `temperature`/`max_iterations` 约束或换模型档位（`21` §3），并把该例标记为软断言。
4. **业务真变化**：规则确实改了 → 按 §5 顺序更新不变量表 → 断言 → 用例。

归因写进用例结果备注，积累三个月就有"契约脆弱点"清单——那是下一轮建模（`19` §2）最好的输入。

## 7. 反模式（禁止）

- 禁止只断言"非空 / 长度 > 0 / 包含某个词"——把值断言降级成形状断言的用例集，退化会一路放行。
- 禁止用真实生产数据未脱敏入集（含客户联系方式/金额）；入集前先脱敏与打码（轨迹上传同理，`13` §2.3 `trace_upload` 默认 `redact=True`）。
- 禁止用 LLM 判官分当发布开关。
- 禁止每次失败都改用例期望去"过"——§6 分类里只有第 4 类允许改期望。
- 禁止 schema 定义与提示词里的字段说明两处各写一份（必然漂移）；从 schema 生成说明文本。
- 禁止把 Golden 集当一次性交付物；没有回流机制（`21` §7）的用例集半年即失效。
