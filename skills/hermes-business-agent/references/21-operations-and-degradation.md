# 21 · 上线后运营视角：可观测、配额、编排与降级契约

> **适用路线**：全路线；标注处随路线不同（①/③/⑤ 自建为主，②/④ 有服务侧原生设施可依）。
> **主线位置**：SKILL.md 第 ⑥ 步（闸门与降级）、第 ⑦ 步（回归取证）、第 ⑧ 步（发布基线）与〔回路〕（运营回流）。
> **与其它参考的分工**：`13` §2.3 = 用量/遥测/追踪模块与签名；`08` §13 = Provider Routing；
> `02` §8 = 路线① 边界清单；`07` §3 = 启动自检与运行数据保护；`20` §4 = 用例回流。
> 本文管的是**能跑通之后**才出现的问题：谁在用、用了多少、跑偏时用户看到什么、错答怎么变成下一条回归用例。

---

## 1. 从"能跑"到"敢用"多出的四件事

上线前后会多出四件业务上看得见的事，本文按依赖顺序逐节解决它们：

1. **看得见**：每次会话的用量、延迟、工具面命中与失败原因要能按用户/时间回放 → 先做 §2（采什么、存哪、别采什么），
   没有这一节后面三件都无据可谈。
2. **管得住**：单次成本与会话成本有上限，超了会熔断，而不是月底看账单才发现 → §3（上限设在哪、熔断给什么信号）。
3. **跑得偏了不伤人**：模型不可用、工具失败、审批被拒时，界面有确定契约，业务数据不会半改未改 → §5（四类故障各一种确定行为）。
4. **有回路**：线上错答能回流成回归用例（`20` §4.1 第三来源），系统随使用变好而不是随使用腐化 → §7。

另外两节不属于这四件事但服务于它们：**§4 编排**回答"要不要多开一个 Agent"，那是第 ② 步形态决策的运营侧余波，
读到那里时手上应该已经有 §2 的用量数据；**§6 发布基线**是把上面四件在上线**前**先量一遍，
好让下一次发版有"退化"可言。

## 2. 可观测性（采什么、存哪、别采什么）

### 2.1 必采字段

| 维度 | 字段 | 来源 |
| --- | --- | --- |
| 身份 | 会话 id、业务用户/角色、（多用户路线）profile | 应用侧登录态；②/④ 路线会话头 `X-Hermes-Session-Id`、记忆作用域 `X-Hermes-Session-Key`（`15` §4） |
| 用量 | prompt/completion/total token、模型名、供应商 | `agent.usage_pricing.normalize_usage(...)` → `CanonicalUsage`（统一口径，禁止直接读各 provider 原始用量；`13` §2.3） |
| 成本 | 估算成本、是否有已知单价 | `usage_pricing.estimate_usage_cost(...)` + `has_known_pricing(...)` |
| 过程 | 迭代轮数、工具调用序列（名/入参摘要/结果状态/耗时） | 构造器回调 `tool_start_callback` / `tool_complete_callback` / `event_callback`（`01` §4） |
| 质量 | 审批结果（通过/拒绝）、校验失败（`20` §3 的 ②③ 两段）、用户纠正/重问次数 | 自建审批层与校验点 |
| 失败 | 错误分类（provider/工具/校验/预算/迭代耗尽/取消） | worker 的 except 分支，必须分类，禁止一律 "error" |

### 2.2 存哪

- 会话本体 Hermes 已存：`hermes_state.SessionDB`（SQLite，`HERMES_HOME` 下），回放消息用 `trace_upload.load_session_messages(session_id, db_path=...)`（`13` §2.3）。
- 业务侧指标另存一张自己的表（一次对话一行 + 工具调用子表），便于按业务维度聚合（哪个部门、哪类单据问得多）。
- 禁止把 Hermes 的会话库当业务数仓直接查写：它是运行时资产，升级可能改形状；导出只走只读。
- 需要外部轨迹分析时用 `trace_upload.upload_session_trace(...)`，**保持默认 `redact=True` / `private=True`**；
  业务数据出域前先过合规（`09` §Step5b 同理）。

### 2.3 禁止采集

禁止明文密钥、provider 凭据、可还原的客户PII、审批人完整身份链、以及整段未经脱敏的业务快照。
日志里出现这些，等于把第 ⑥ 步的护栏换成一个泄漏面。

## 3. 配额与成本治理

分层设限，别只设一个全局上限：

| 层 | 手段 | 建议起点 |
| --- | --- | --- |
| 单回合 | `AIAgent(max_iterations=...)` **必须显式设**（默认值与「文档 vs 源码」不一致的结论唯一见 `01` §3，此处不重述） | 业务问答 10~30；带多步工具的写面 20~40 |
| 单会话 | 累计 token/成本超阈值后**降级不降级体验**：切只读面 + 提示用户转人工 | 按业务单笔价值定 |
| 按用户/日 | 自建计数器（宿主侧），命中即拒并给明确文案 | 防单人跑飞拖垮共享额度 |
| 模型档位 | 只读问答走小/便宜模型，写面与结构化结论走强模型；供应商不可用时的回退用 Provider Routing（`08` §13，配置见 `hermes_cli` 的 providers/models 模块，`10`） | 路由规则要能被 §2 的字段回放验证 |
| 缓存与压缩 | 长会话注意上下文压缩行为（`13` §2.1），避免"越问越贵" | 观测 `usage` 随轮数的曲线 |

**成本口径的诚实性**：路线①/⑤（无网关计费）下 `get_credits_*` 与 `estimate_usage_cost` 都是**估算**，
界面与报表必须写"估算"字样（`07` R7）；`has_known_pricing(...)` 为假时要显示"未知单价"而不是显示 0。
账号侧余量可用 `agent.account_usage` / `agent.credits_tracker`（学分耗尽会生成 `AgentNotice`，`13` §2.3），
把"额度将尽"变成界面提示，禁止让它表现为一次普通失败。

## 4. 多 Agent 编排（什么时候真需要）

默认不要编排。单 Agent + 对的上下文能解决绝大多数业务问答与操作；编排带来的调试与成本复杂度不对称。
确实需要时，**按下面顺序问，越靠前越便宜**（第一行不改拓扑，往下每行都多一套运行时或一份配置）：

| 需求 | 机制 | 事实与注意 |
| --- | --- | --- |
| 多个场景要的**能力不同、运行时可以相同** | **本节不管这件事怎么定**：一套运行时 + 入口差异配置化的判据、三条代价、表形状，全在 SKILL.md 第 ② 步与 `19` §7 入口表。这里只记它是"先合后拆"里最便宜的一档（换面不改拓扑，上下文/预算/审批链路都只有一份） | 禁止用 `toolset_distributions` 做按场景换面（按概率抽样，实测可把禁止面抽进球面，`11` §9）；该用的是确定性解析 API（`11` §8） |
| 一个子任务要独立上下文（长检索、独立试错） | 内核 `delegation` 工具集（`delegate_task`，`03` §3.6，实现 `tools.delegate_tool`） | 禁止在**未实测**前宣称"界面能显示委派卡片"：`event_callback` 是否透传委派事件未实测（`07` R6），先实测再决定渲染 |
| 多套业务配置/记忆彼此隔离 | Profiles（`08` §11；②/④ 路线 `hermes -p <name> gateway`，`15` §3 多用户隔离） | 每 profile 独立 `HERMES_HOME` 子树，备份与门禁各自算 |
| 多个模型对同一输入投票/融合 | MOA（`08` §3，预设解析可 `hermes_cli.moa_config` 复用，`02` §4） | 成本按模型数放大，先算 §3 的预算 |
| 长任务、跨进程持久工作队列 | Kanban worker lanes（`08` §14） | 属跨进程形态，选路线时一并定（`02` §2.2–§2.5） |
| 常驻目标推进 | Goals（`08` §1，含进程内实战写法） | — |

**先合后拆（本节只判这一件事：先收敛工具，再谈拆 Agent）**：出现"一堆同类查询/检索工具"时，第一选择是**把它们收敛成一个统一入口工具**
（减面、减每轮 token、减模型的选择负担），收敛稳定后确实还需要独立上下文与独立试错，才谈拆子 Agent。
"多场景"那一半不在本节——合并运行时与入口配置化在第 ② 步就定完了（判据、代价、入口表见 SKILL.md 第 ② 步与 `19` §7）。
顺序反了会得到一组互相重叠的工具和一条谁也说不清调了哪个的链路。

**硬约束（全路线通用）**：`AIAgent` 非线程安全、**不可共享实例**——子 Agent 各自新建（SKILL.md 第 ③ 步铁律）；
每个 Agent 的工具面按其角色单独裁剪（禁止子 Agent 继承父的全量面，`19` §3 逐角色重算）；
编排层级要能由回调/事件在日志里还原（§2.1 的工具调用序列是唯一凭据）；
子 Agent 之间隔离的不只是上下文——**各自的产物路径与"完成"状态也要各自一份**
（并发写同一份报告或共用一个 done 信号，表现就是结果串台，且只在多任务同时跑时才出现，最难复现）。

**文件作用域与凭证这两维，实测下来是"各走各的"而不是"关在各自笼子里"**（0.19.0，`tools/delegate_tool.py`）：
子 Agent 有自己的 task_id（`:1952`），它就是 spawn 前预建的 `subagent_id`——格式 `sa-<序号>-<8 hex>`（`:1118`；
拿不到预建 id 时才回退成 `subagent-<序号>-<8 hex>`），文件缓存与 terminal 状态按它分开；
但它的起始 cwd **由父播种**（`:1961-1963` `record_session_cwd(child_task_id, get_session_cwd(parent))`），
且父子同在一个宿主文件系统、同一份写白名单（`HERMES_WRITE_SAFE_ROOT`，默认可见即全盘）之下
——**换 task_id 不等于换根目录**。并发写同一文件有检测（父子 `known_reads` 快照比对，`:2233-2239`），那只是撞车告警，不是隔离。
per-task 可覆写的只有 `terminal` 后端的镜像与 cwd（`register_task_env_overrides`，`tools/terminal_tool.py:1125`），
**没有 per-task 密钥**：子 Agent 要用不同凭证，只能靠 profile / 独立 `.env`（`06` §9.5）或干脆拆进程。
⇒ 上面这些维度（上下文、工具面、状态与产物、完成条件、**文件作用域**、**访问凭证**）里，
后两维要真隔离，做法是把动作推到不同**进程/容器**，禁止靠拆子 Agent 达成。

## 5. 降级交互契约（四类故障，四种确定行为）

业务界面最忌讳的是"转圈无响应"和"静默给出半截结果"。四类故障各自确定降级契约，并写进 §6 的用例。

| 故障 | 界面契约 | 数据一致性 | 可否自动重试 |
| --- | --- | --- | --- |
| **provider 不可用 / 超时** | 明确文案（"模型暂不可用，已保留你的问题"+ 重问按钮），禁止空白气泡 | 无写操作发生 | 可（有退避与次数上限） |
| **工具执行失败** | 工具卡片显示失败态与原因摘要，允许"跳过此步/改用只读方式" | 失败工具不得留下部分写入（handler 内原子化） | 视错误类别；**任何重试前先读当前状态**（`19` §3 第 2 步第 3 条），参数错可重问，权限错不重试 |
| **审批被拒** | 显示被拒动作 + 原因 + 后续可行路径（走人工），Agent 继续对话但写面本次关闭 | **未执行**，必须显式呈现"未执行" | 不得自动重问以图绕过审批 |
| **迭代/预算耗尽** | "已达本轮上限，以下是已完成部分"（附已完成清单），提示可拆分继续 | 已完成部分必须自洽，禁止停在中间态 | 可（拆分续跑，带上下文；**续跑前按幂等键读状态**，禁止重放写操作） |

实现要点：

- 错误事件走同一条 queue 通道（`02` §3 的 `("error", msg)` 分支），禁止在 worker 线程里直接改界面（`07` 铁律）。
- 静默降级的探测器：真实对话断言 `stream_callback` 被调 ≥1 次（SKILL.md 第 ⑦ 步 Test 第 3 项）。
  一次性吐全文是"降级"最常见形态——用户只觉得慢，你以为是正常。
- 界面渲染错误路径时**不再发 done 事件**（`02` §3 已核实行为），前端状态机要按此写，禁止等 done 事件收尾——那会让界面停在无响应状态。
- 降级路径全部要有 §2.1 的失败分类日志，否则第 6 个月的线上问题无从归因。

## 6. 发布前基线（把运营视角前移到第 ⑧ 步）

上线前留一组可比对的数字，之后每次发版对比：

1. **通过率**：Golden 集（`20` §4）分维度通过率——只读面 / 受控写面 / 越权负例 / 降级四类，分开看。
   禁止只看总通过率，会被"负例全崩、正例全对"平均掉。
2. **成本曲线与轮次**：典型 5 个业务任务的平均 token 与估算成本（标注"估算"），与上一版差值；
   **同时记"完成任务用的工具往返轮次"**（走 `agent.usage_pricing` 统一口径）。成本是个乘式：
   **每轮注入量（≈ 系统提示 + 快照 + 面宽 schema + 历史）× 轮次**——第 4 条量的是乘式的左边，轮次是右边，禁止只报左边。
   把 N 步机械链折成 1 步省的是 **N 次全量重放**，这是"折轮次"唯一的账面理由（禁止因为它看起来高级）。
3. **延迟分布**：首字延迟（流式体验）与整轮完成延迟的 p50/p95，来自 §2 的过程字段。
4. **面宽与面成本**：实际开放工具/工具数量（`19` §6 的 diff 输出）+ **每轮工具定义占用的 token**，
   禁止允许"悄悄多开两个"过版。面宽过大时的解法是加发现层或收敛工具（`19` §6），不是砍功能也不是放任。
5. **审批健康度**：批准率与回滚率（§2.1 的审批字段）。批准率接近 100% 是**仪表告警**而不是好消息——
   说明确认已退化成形式，按 `19` §3 的分级判据复查该不该把动作挪进禁止面；回滚率 > 0 时不得放量。
6. **门禁**：`release_gate --verify-launch`（选路线④⑤ 再加 `--api-server`）+ 三系统形态的 `verify_tristructure.py` 全绿；
   选了 ②/④ 常驻服务的，把"重启后自恢复 + 健康端点恢复"列为一条验收用例。

**轮次这一维先算清"折轮次的路走不走得通"再动手**（免得后人重跑一遍实测）：内核里能折轮次的能力是 `execute_code`
（Programmatic Tool Calling——让模型写一段脚本、在脚本里调工具，把多步链折进单轮推理，中间结果不进上下文；
**能力事实与边界逐条实测归 `03` §3.4**，含"Windows 到底能不能用"那条与 docstring 相反的结论）。
它的硬限制是**沙箱可调工具只有固定 7 个白名单、里面没有任何业务工具** ⇒ 对业务多步链（查单据 → 校验 → 写回）它折不动。
所以按便宜到贵，省 token 与省轮次的主路子是：

1. **归属下沉**：确定性环节按 `19` §3 第 5 步判给代码、连工具都不注册——既少一份 schema，又少一轮往返，最便宜的一档。
2. **统一入口工具收敛**：把"必须按顺序跑完的多步业务链"做成**一个**工具、内部跑完只回一个结构化结论
   （第 ⑤ 步动作 6 的"先合再拆"）。
3. **快照瘦身**：`19` §4.2 五行预算表里「实时快照」那一行，按预算砍聚合值 / Top-N。
4. **按场景换面**：用确定性解析 API 换工具集（`11` §8；禁止§9 的采样档），怎么按入口配是第 ② 步的事（入口表 `19` §7 第 6 张）。
5. **编排 / 拆子 Agent**：§4，最贵的一档，判据也在那里。

`execute_code` 排不进前五，除非需求本身就是"内核文件 / 检索 / 网页链的多步批处理"（那是它的主场）。
禁止为了账面轮次好看去用它绕业务闸门——那一条是红线，见 `07` R13。

## 7. 运营回路（错答 → 用例 → 发版）

```
线上错答/越权尝试/降级触发
   │ ① 采：§2.1 字段 + 用户纠正动作（一次点击即可）
   ▼
   ② 归因：按 `20` §6 四类分（契约漂移 / 装配故障 / 模型波动 / 业务真变化）
   │    装配与契约类 → 直接修，不改用例期望
   ▼
   ③ 沉淀：脱敏后入 Golden 集（`20` §4.1 第三来源），同 PR 带修复、提交信息带那张单的号（SKILL.md 〔回路〕）
   │    文档与源码冲突 → 记 `docs/troubleshooting.md`
   ▼
   ④ 回归：`20` §4.4 各段跑一遍 + §6 基线对比
   ▼
   ⑤ 发版：SKILL.md 第 ⑧ 步门禁 → 重打包/重部署（版本互斥 venv 见 `06` §5）
```

**刚发出去那一段不归本节这条回路，归 SKILL.md 第 ⑧ 步写定的观察窗**（判的是要不要回退）；窗收口之后才是下面的常态节奏。
节奏建议：每周批量归因一次（不建议逐条即时反应），每月看一次 §6 那组基线的趋势，每季度做一次用例集健康评审
（`20` §5 的淘汰与补入成对发生）。**这三条要在本期收口那一页上逐条有人认领**（SKILL.md 第 ⑧ 步末拍），
答不出就写"无人"，禁止空着不填。Hermes 自身会沉淀记忆与技能（`08`、`13` §2.2），
**记忆后端只允许一个外部 provider**（`13` §2.2 关键约束），要长期个性化就选定其中一个，禁止两个后端并存、各自返回不一致的记忆。

## 8. 反模式（禁止）

- 禁止只在界面上报错、不落分类日志；上线一周后无从归因。
